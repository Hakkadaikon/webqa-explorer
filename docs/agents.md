# Claude Codeの役割分担

このリポジトリでは、Claude Codeの親セッションとサブエージェントで作業を分ける。
品質の下限は品質ゲート(整形、lint、複雑度、カバレッジ100%)が機械で保証する。
そのため、実装の大半は軽いモデルに任せ、ゲートが測れない判断だけを強いモデルが受け持つ。

## 役割

| 役割 | 担当 | モデル | 受け持つもの |
|---|---|---|---|
| 親セッション | (メインの会話) | Opus | アーキテクチャ、計画、テスト設計、統合 |
| 実装 | `agents/implementer.md` | Sonnet | 1タスク分の TDD |
| 機械的な直し | `agents/fixer.md` | Haiku | 整形、lint の指摘、複雑度の超過 |
| レビュー | `agents/reviewer.md` | Opus | テストの強さ、配線、ゲートの回避 |

agentの定義は`agents/`に置き、`.claude/agents`をそこへのリンクにしている。

## 親セッションが決めること

テストの網羅と強さは、ゲートでは測れない。
カバレッジ100%は、何も確かめないassertでも満たせるからだ。
そこで、何を確かめるかは親セッションが決め、実装担当に渡す。

実装担当へのbriefには、次を必ず書く。

- タスクの内容と、触ってよいファイル
- 失敗させるテストの名前と、確かめる期待値
- 受け入れ条件

テストの強さは、PRで回るmutationテストが機械で裏を取る。

## 流れ

1. 親セッションが、テスト項目の台帳からタスクとbriefを作る。
2. implementerがTDDで実装し、`just check`を通してコミットする。
3. 整形やlintだけで落ちたときは、fixerに直させる。
4. reviewerが差分を見る。mustが残れば2に戻す。
5. 親セッションが統合し、pushする。

## 並列に回すとき

触るcrateやモジュールが重ならないタスクは、worktreeを分けて並列に回せる。
worktreeはそれぞれ丸ごとビルドするので、立てる前、立てたあと、終わったあとに次を守る。

- 立てる前に`df`で空きを見て、並列の数を決める。
  目安は1本あたり500MB(このリポジトリで測った値)である。
  `--in-place`を付けないmutationは木を丸ごと写すので、もう1本分が要る。
- briefで参照するのは、worktreeの中から読めるファイルだけにする。
  設計の文書が未コミットなら、先にコミットしてからworktreeを立てる。
- 立てたあと、worktreeの中で最初に`just worktree-tools`を実行させる。
- ビルドの成果物は、`just`を通すと本体のcheckoutの`target/`に置かれる。
  依存は1回のビルドで使い回され、cargoのロックで同時のビルドは1本ずつになる。
  `cargo`を直接叩くときは、`CARGO_TARGET_DIR`に同じ場所を渡す。
  共有しているので、worktreeの片づけに`cargo clean`は使わない。
- メモリが少ないマシンでは、担当に`CARGO_BUILD_JOBS=2`を渡す。
- TDDの途中は、触っているモジュールのテストだけを回す。
  例えば`cargo test -p webqa-core screen`のようにする。
  カバレッジの計測は、コミットの前に1回だけ回す。
- 並列のときは、mutationを担当に回させない。
  同時に回すとマシンを取り合うので、親セッションが統合の前に1本ずつ回す。

## 格上げの規則

次のときは、同じimplementerをOpusで起動し直す。
Agentツールの`model`に`opus`を渡せば、定義を変えずに切り替わる。

- implementerが、同じゲートで3回続けて落ちてBLOCKEDを返したとき
- 並行処理、async、ライフタイムの設計が要るタスク
  (この場合は最初からOpusで起動する)
- fixerが、振る舞いを変えないと直せないと返したとき

## 割り当ての見直し

最初の数タスクは、同じタスクをSonnetとOpusの両方で実装して比べる。
比べるのは次の3つ。
ゲートで落ちた回数、reviewerの指摘の数、mutationの生き残りの数。
差が小さければ割り当てを保ち、大きければOpusの受け持ちを広げる。
