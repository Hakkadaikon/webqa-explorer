# 設計検討の記録(`tasks/`)

`tasks/`には、実装の前に行った設計検討の記録を置いている。
このページは、その記録の読み方をまとめたもの。

## コミットしている理由

`tasks/`の中身は、要件の抽出、設計の検査、テスト項目の洗い出しの作業記録である。
こうした作業記録は、本来はリポジトリにコミットしない想定のものだ。
このリポジトリでは、設計がどう固まっていったかを後から追えるよう、あえてコミットしている。

実装の仕様と受け入れ条件は、`docs/`と`crates/`のテストに引き継ぐ。
そのため、`tasks/`を読まなくても実装は追える。
設計判断の根拠を遡りたいときに読んでほしい。

## 検討の進め方

設計の検討には、Claude Codeのプラグイン[hymme](https://github.com/Hakkadaikon/hymme)を使った。
hymmeのloop-engineeringという手順に沿って、次の順に進めた。

1. 元の要求から要件を抽出し、EARS記法で書き直す。
2. 状態遷移をTLA+の仕様に書き起こす。
3. TLCで全状態を検査し、不変条件と終了性を確かめる。
4. 仕様に機械的な変異を入れ、検査が変異を見逃さないかを確かめる。
5. 仕様の文面を独立した読み手に言い直させ、要件と食い違っていないかを確かめる。
6. 受け入れシナリオをGherkinで書く。

元の要求は、iOSアプリ向けの探索的テストツール(判断モデルJevを使うもの)の記事と、
それをWebサービス向けに作り直したいという要望である。

## `tasks/loopeng/`の中身

作業の引き継ぎの起点は`tasks/loopeng/HANDOFF.md`になる。
ほかのファイルは次のとおり(ファイル名の頭はすべて`WebExploratoryQA`)。

| ファイル | 工程 | 内容 |
|---|---|---|
| `.extract.md` | 1 | 要件の抽出台帳。トレーサビリティ表と、STRIDE・CWEによる脅威の洗い出しを含む |
| `.model.md` | 2 | 状態とドメインのモデル(状態変数、遷移、不変条件) |
| `.tla` / `.cfg` | 2〜3 | TLA+の仕様と、TLCの設定 |
| `.tlc-run.log` | 3 | TLCの実行記録 |
| `.mutants-v*.tsv` | 4 | 仕様に入れた変異ごとの結果。v1は旧仕様、v3が現行 |
| `tools/classify_mutants.py` | 4 | 変異の結果を種類ごとに分類するスクリプト |
| `.faithfulness-input.md` / `.faithfulness.md` | 5 | 読み手に渡した仕様の文面と、要件との突き合わせ |
| `.reach.log` | 5 | 性質の前提が実際に起こりうることを確かめた記録 |
| `.feature` | 6 | 受け入れシナリオ(71本) |

TLCは反例を出さなかったので、反例から作ったシナリオは無い。
受け入れシナリオは、要件から正常系・異常系・境界を書き起こした。

## `tasks/test-design/`の中身

テスト項目の台帳を置いている。
台帳の1行が、テストすべき振る舞い1つに対応する。

| ファイル | 対象 | 状況 |
|---|---|---|
| `WebExploratoryQA.md` | 受け入れシナリオ(71本を1件ずつ転記) | テスト手法とテスト名は未割り当て |
| `metrics-script.md` | `scripts/metrics.py` | 実装済み、テストは緑 |
| `commit-msg.md` | `scripts/commit_msg.py` | 実装済み、テストは緑 |

台帳の`テスト対象:`の行には、その台帳が受け持つテストファイルを書く。
hymmeのフックは、書こうとしているテストファイルに対応する台帳が閉じていないと、作成を止める。
