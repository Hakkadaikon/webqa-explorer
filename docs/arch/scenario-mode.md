# 決め打ちシナリオモード

## 目的

決め打ちシナリオモードは、利用者が書いた段階を順に進め、決まった流れが最後まで通るかを確かめる。
各段階には、判断モデルに渡すゴールと、段階を終えたと判定する条件`done_when`を書く。
段階の中でどの要素をどう操作するかは、判断モデルが選ぶ。
次の段階へ進むかは、判断モデルの答えではなく、中核が`done_when`で判定する。

## 入力

決め打ちシナリオモードは次のコマンドで動かす。

```text
webqa run --config <設定> [--out <出力先>]
```

出力先を省くと`.webqa`に書く。
引数と終了コードは[cli.md](cli.md)にまとめた。

設定の項目は、探索モードと同じものに`scenario`を足したものである。
項目の形と既定値は[config.md](config.md)に、探索モードと共通の項目の使い道は[explore-mode.md](explore-mode.md)にある。

`scenario`は次の形で書く。

```yaml
scenario:
  stages:
    - name: ログイン
      goal: ログインを済ませる
      done_when:
        url: /home
        element: { role: button, name: ログアウト }
```

| 項目 | 中身 |
|---|---|
| `name` | 段階の名前 |
| `goal` | 判断モデルに渡すゴールの文 |
| `done_when` | 段階を終えたと判定する宣言の組 |

`scenario`が無いと、設定エラーで起動しない。
`stages`が空のときと、`ops`が`enter`だけのときも、設定エラーにする。
`ops`が`enter`だけで`scenario`も無いときは、`scenario`が無いことの設定エラーを先に出す。
`enter`だけの設定をエラーにする理由は[safety.md](safety.md)の「禁止要素とenter」にある。

## 振る舞い

1つのステップの流れは探索モードと同じで、状態遷移の全体は[core.md](core.md)に書いた。
ここでは決め打ちシナリオモードに固有の振る舞いを書く。

### 段階の進め方

段階は、書いた順に1つずつ進める。
中核は、判断モデルに問う前に毎回、今の段階の`done_when`を最新の観測で判定する。
成り立てば、次の段階へ進む。
最後の段階で成り立てば、ゴール達成で終わる。
判定するのは今の段階だけで、後の段階の`done_when`は見ない。

段階を進めたときに戻すものと戻さないものは、[core.md](core.md)の「カウンタ」に書いた。

### 判断モデルへの問い

判断モデルには、次のことを問う。

- 操作の種類
- 対象の要素
- 画面にエラーの表示があるか
- 今の段階のゴールを達成したか

操作の種類の選択肢は、`ops`に書いた種類すべてである。
ただし、禁止要素のある画面では`enter`を外す。
理由は[safety.md](safety.md)の「禁止要素とenter」に書いた。
探索モードと違い、表示中の入力欄に値があるかでは外さない。
対象の要素の選択肢は、表示領域の中のすべての要素である。
探索モードと違い、候補の段で絞らない。

ゴールを達成したかの答えでは、段階を進めない。
段階を進めるかは、`done_when`の判定だけで決める。

### 操作の種類

操作の種類と、ブラウザでの振る舞いは探索モードと同じである。
表は[explore-mode.md](explore-mode.md)の「操作の種類」にある。
決め打ちシナリオモードでは、それに`done`が加わる。

| 操作 | 振る舞い |
|---|---|
| `done` | 段階を終えたと判断モデルが宣言し、実行を終える |

`done`で終わったときの終了理由は`reported_done`で、`done_when`の判定を通っていない。
`done_when`が成り立って終わるゴール達成(`goal_achieved`)とは、終了理由で区別する。

### 終わり方

決め打ちシナリオモードは、次のどれかで終わる。

| 終了理由 | 起きるとき |
|---|---|
| ゴール達成(`goal_achieved`) | 最後の段階の`done_when`が成り立った |
| 判断モデルの宣言(`reported_done`) | 判断モデルが`done`を選んだ |
| 行き詰まり(`stuck`) | 進展の無いステップが`limits.stuck_threshold`に達した。または判断モデルが`stuck`を選んだ |
| 判断予算切れ(`budget_exceeded`) | 問い合わせの回数が`limits.max_decisions`に達した |
| 時間切れ(`time_exceeded`) | 経過時間が`limits.max_duration_secs`に達した。時間窓が満杯で、次の窓が明けるのがそれと同時か後のときも含む |
| 中断(`user_aborted`) | 利用者が止めた |

進展の数え方は[core.md](core.md)に、判断予算と制限時間は[safety.md](safety.md)に書いた。

## 出力

出力は探索モードと同じで、実行ごとのイベントログ、実行結果、スクリーンショットと、探索の記憶である。
中身は[records.md](records.md)に、探索の記憶は[explore-mode.md](explore-mode.md)に書いた。
決め打ちシナリオモードでも探索の記憶を更新するが、候補の絞り込みには使わない。

## 設計の詳細

### done_whenの宣言

`done_when`は、次の3種類の宣言の組で書く。

| 宣言 | 成り立つとき |
|---|---|
| `url` | 今のURLのパスが一致する |
| `element` | 指定したroleと名前の要素がページにある |
| `text` | 指定したテキストがページにある |

1つの段階に書いた宣言がすべて成り立ったときに、その段階を終えたとみなす。
宣言を1つも書かない段階は、成り立たない。

各宣言の判定のしかたは次のとおり。

- `url`は、`/`で始まり`//`で始まらないパスで書く。
  今のURLを基準に解決したパスが、今のURLのパスと一致すれば成り立つ。
  クエリとfragmentは比べない。
- `element`は、roleと名前の両方を書く。
  roleと名前が完全に一致する要素がページにあれば成り立つ。
  見出しのような操作できない要素も指せる。
- `text`は、空白だけでない文字列を書く。
  ページ全体のテキストにその文字列が含まれていれば成り立つ。

### 判定の材料

判定は中核の純粋な関数で行う。
材料は、最新の観測のページ全体の要素、ページ全体のテキスト、URLだけである。
表示領域の外の要素とテキストも材料に入る。

材料は伏せ字の処理を通したあとのページである。
伏せる値を含む名前やテキストは、`[[名前]]`に置き換わった形で比べる。
伏せ字の処理は[safety.md](safety.md)に書いた。
