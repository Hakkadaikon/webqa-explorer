# コマンド

`webqa`は実行ファイル1つで、サブコマンドで動きを選ぶ。
イベントログを表示する画面も、`webqa watch`のサブコマンドで別のプロセスとして起動する。
コマンドの定義は`crates/webqa/src/cli.rs`にあり、引数はclapで読む。

## サブコマンド

```text
webqa run --config <設定> [--out <出力先>]
webqa explore --config <設定> [--out <出力先>]
webqa replay <実行結果> --config <設定> [--out <出力先>]
webqa interview --config <設定> [--out <出力先>] [--previous <前回の台帳>]
webqa check-docs <persona|purpose> <ファイル>
webqa watch <実行のディレクトリ>
```

| サブコマンド | すること | 詳しい文書 |
|---|---|---|
| `run` | 設定の`scenario`に沿って、決め打ちシナリオを実行する | [決め打ちシナリオのモード](scenario-mode.md) |
| `explore` | 対象を自由に探索する | [探索モード](explore-mode.md) |
| `replay` | 実行結果に記録した判断モデルの答えで、実行をやり直す | この文書の「再実行」 |
| `interview` | ペルソナになりきって、試行を重ねる | [インタビューのモード](interview-mode.md) |
| `check-docs` | ペルソナか目的の文書の形式だけを検査する | [インタビューのモード](interview-mode.md) |
| `watch` | 実行のイベントログを追って、端末に表示する | [問題の記録と実行結果](records.md) |

`run`、`explore`、`replay`は、中核の状態機械を同じ実行ループで回す。
`interview`は、試行ごとに同じ実行ループを回す。
`check-docs`と`watch`は、実行を始めない。
`--help`と`--version`も受ける。

## 引数

| 引数 | 受けるサブコマンド | 既定 | 中身 |
|---|---|---|---|
| `--config <設定>` | `run`、`explore`、`replay`、`interview` | 無し(必須) | 設定ファイル。項目は[設定](config.md)にある |
| `--out <出力先>` | `run`、`explore`、`replay`、`interview` | `.webqa` | 記録の出力先のディレクトリ |
| `--previous <前回の台帳>` | `interview` | 無し | 照らし合わせる前回の台帳 |
| `<実行結果>` | `replay` | 無し(必須) | やり直す実行の`report.json` |
| `persona`か`purpose` | `check-docs` | 無し(必須) | 文書の種類 |
| `<ファイル>` | `check-docs` | 無し(必須) | 検査する文書 |
| `<実行のディレクトリ>` | `watch` | 無し(必須) | `<出力先>/runs/<実行ID>`のディレクトリ |

引数の誤りは、clapの文を標準エラーに書き、終了コード2で終わる。
`--help`と`--version`は、標準出力に書いて0で終わる。

## 起動の流れ

どのサブコマンドでも、最初に作業ディレクトリの`.env`を読む。
読み方は[設定](config.md)の「環境変数」にある。
次に、環境変数`PLAYWRIGHT_NO_SIGNAL_HANDLER`を立てる。
そのあとで診断用のログを始め、引数を読む。
この2つの環境変数の操作は、プロセスのスレッドが1本のうちに済ませる。
理由は[ランタイム](runtime.md)にある。

`run`、`explore`、`replay`は、次の順に起動する。
どれかの段で失敗したら、そこで止まる。

1. 設定ファイルを読む。
2. `replay`なら、実行結果を読む。インタビューの実行結果は設定エラーにする。
3. 設定を検証し、モードに応じた検査を行う。
4. `replay`なら、実行結果に残した開始時の記憶を読む。
5. 判断モデルを起動する。`replay`では、実行結果を再生する判断モデルを使う。
6. ブラウザを1280×720の大きさで起動する。
7. 出力先に実行のディレクトリを作る。
8. 実行ループを回す。

1から4の段の失敗は設定エラーで、終了コード2で終わる。
5の段は、`judge.kind`か`judge.command`の誤りなら2、起動の失敗なら3で終わる。
6と7の段の失敗は実行時エラーで、3で終わる。
実行の時計は、ブラウザが起動したあとで動かし始める。
実行IDは、ブラウザが起動したあとの時刻をUTCのミリ秒まで書いたものである。
形は`20261018T020000.123Z`のようになる。

`interview`は、設定とペルソナと目的の文書を読み、前回の台帳を確かめてから、判断モデルを起動する。
ブラウザは試行ごとに開き直す。
流れの詳細は[インタビューのモード](interview-mode.md)にある。

実行が終わると、終わり方を1行で標準エラーに書く。

| 終わり方 | 書く文 |
|---|---|
| 終了理由を記録して終わった | `終了理由 <終了理由>、記録 <実行のディレクトリ>` |
| インタビューが台帳を書いて終わった | `終了理由 <completed、time_up、interruptedのどれか>、台帳 <台帳のパス>` |
| インタビューの初期化のコマンドが失敗した | `<エラーの文>、台帳 <台帳のパス>` |
| インタビューで前回の台帳と今回の実行が合わなかった | 合わない点を述べる文だけ |
| 記録を書き終える前に中断した | `記録を書き終える前に中断した` |
| 実行時エラーで止まった | エラーの文 |

終了理由の名前は、`report.json`の`reason`と同じである([問題の記録と実行結果](records.md))。

## 再実行

`webqa replay`は、実行結果の`report.json`を台本にして、実行をやり直す。
実行結果に記録したモードで動き、設定はその都度`--config`で渡す。
判断モデルの代わりに、記録した答えを順に返す`Replay`を使う。
`Replay`の振る舞いは[判断モデル](judge.md)の「実行結果の再生」にある。
入力欄に打つ値は、渡した設定の`inputs`から補う。

実行結果の形式の版`schema`が1でなければ、設定エラーにする。
読めない実行結果も設定エラーにする。

再実行は、実行結果の`start_memory`に残した探索の記憶から始める。
出力先の記憶のファイルは、読みも書きもしない。
そのため、同じ出力先で再実行しても、元の実行が書いた記憶で候補の絞り込みは変わらない。
`start_memory`が無い実行結果は、空の記憶から始める。
`start_memory`が別のオリジンの記憶なら、空の記憶から始める。
ポートの違う環境での再実行などが、これに当たる。
`start_memory`が記憶として読めなければ、設定エラーにする。
記憶の中身は[探索モード](explore-mode.md)にある。

## 文書の検査

`webqa check-docs`は、ペルソナか目的の文書を1つ読み、形式だけを検査する。
正しければ何も書かずに、終了コード0で終わる。
誤りがあれば、項目の名前を含む文を標準エラーに書き、2で終わる。
文書を読めないときも2で終わる。
ブラウザも判断モデルも起動しない。
文書の形式は[インタビューのモード](interview-mode.md)にある。

## 実行の表示

`webqa watch`は、別のプロセスで動く実行のイベントログを追い、端末に表示する。
実行のディレクトリが無ければ、標準エラーに`実行のディレクトリが無い`と書き、終了コード2で終わる。
それ以外では、Ctrl-Cを受けるまで表示を続け、0で終わる。
表示の中身は[問題の記録と実行結果](records.md)にある。

## 終了コード

| コード | 意味 |
|---|---|
| 0 | 終了理由を記録して終わり、確定の問題を見つけなかった |
| 1 | 終了理由を記録して終わり、確定の問題を見つけた |
| 2 | 設定エラーか引数の誤りで、実行を始めなかった |
| 3 | 実行時エラーで止まった |

終了コードは`crates/webqa/src/exit.rs`で決める。
数えるのは確定の問題だけで、参考情報の問題は数えない。
問題の区分は[問題の記録と実行結果](records.md)にある。
中断で終わったときも、記録を書き終えれば、見つけた問題の有無で0か1にする。
記録を書いている間の2回目のCtrl-Cで、書き終えずに終わったときは3にする。
記録の書き込みに失敗したときと、ブラウザの操作に失敗したときも3にする。

`interview`の終了コードも同じ決め方で、確定の問題が記録されたときだけ1にする。
台帳に載せる課題は数えない。
前回の台帳を読めないときと、前回の台帳が今回の実行と合わないときは、2にする。
試行の前の初期化のコマンドが失敗したときは、3にする。

`check-docs`は、検査が通れば0、通らなければ2にする。
`watch`は、Ctrl-Cで終えれば0、実行のディレクトリが無ければ2にする。

起動の途中のCtrl-Cは、この表のどれでもない終わり方をすることがある。
その終わり方は[ランタイム](runtime.md)の「中断」にある。

`main`は`std::process::ExitCode`を返し、`std::process::exit`は使わない。
clippyの`exit`の検査を守るためである。
