# 問題の記録と実行結果

1回の実行は、見つけた問題、実行結果、イベントログを出力先に残す。
イベントログは、別のプロセスで動く`webqa watch`の画面が読んで表示する。
インタビューのモードが書く台帳は、[インタビューのモード](interview-mode.md)にある。

## 出力先の構成

出力先は、コマンドの`--out`で決まり、既定は`.webqa`である([コマンド](cli.md))。

```text
<出力先>/
  memory/
    <オリジン>.json         探索の記憶
  runs/
    <実行ID>/
      events.jsonl          イベントログ
      report.json           実行結果
      ledger.md             インタビューの台帳(インタビューのモードだけ)
      screenshots/          問題を見つけたときと、台帳の課題のスクリーンショット
```

記憶のファイル名の`<オリジン>`は、オリジンをURLエンコードした文字列である。
英数字と`-`、`.`、`_`、`*`のほかのバイトは、`%XX`の形で書く。
実行IDの決め方は[コマンド](cli.md)にある。
同じ実行IDのディレクトリがすでにあれば、実行時エラーで止まる。
探索の記憶は、実行をまたいで使う。
中身は[探索モード](explore-mode.md)にある。

記録に書く文字列は、どれも伏せ字を通す。
`report.json`は全体を伏せ字に通してから書き、イベントログも1行ずつ伏せ字に通す。
伏せ字の仕組みは[安全のための仕組み](safety.md)にある。

## 問題の種類

| 種類(`kind`) | 根拠 | 区分(`class`) |
|---|---|---|
| `error_display` | 判断モデルが答えた、エラー表示のある確率が閾値以上 | 確定(`confirmed`) |
| `accessible_name` | 要素の読み上げ名が、画像ファイル名や仮の値に一致する(中核が判定する) | 確定(`confirmed`) |
| `console_error` | ブラウザのコンソールにエラーが出た | 確定(`confirmed`) |
| `outside_domain` | 遷移したあとのURLが許可ドメインの外にある | 確定(`confirmed`) |
| `semantic` | 意味の判断が要る検出で、判断モデルだけが判定する | 参考情報(`reference`) |

終了コードに数えるのは、確定の問題だけである([コマンド](cli.md))。
`error_display`と`semantic`の閾値は、設定の`limits.error_confidence`である。
確率の無い答えからは、問題を記録しない。
`semantic`の問題には、決まった名前(`わかりにくい表示`など)を付ける。
この名前は問いの側で決め、画面の文字列を含めない。
`accessible_name`は、表示の範囲の外の要素も含めて、画面のすべての要素を調べる。
`console_error`は、1回の観測で同じ文のエラーが続いても1つにまとめる。
`net::ERR_INTERNET_DISCONNECTED`と`net::ERR_NETWORK_CHANGED`を含むエラーは、問題にしない。
手元の回線が切れたときに出るエラーで、ページの不具合ではないからである。
`net::ERR_NAME_NOT_RESOLVED`のような、ほかの通信のエラーは問題として残す。

## スクリーンショット

問題を見つけたら、その画面のスクリーンショットを残す。
ファイル名は`ISSUE_<種類>_step<ステップ番号>.png`にする。
インタビューのモードでは、試行どうしで名前がぶつからないように、`ISSUE_<種類>_trial<試行番号>_step<ステップ番号>.png`にする。
スクリーンショットは画面をそのまま残し、伏せ字にしない。
撮れなかったときは、ファイルを残さず、記録からもスクリーンショットの項目を省く。

## 実行結果

`report.json`は、実行の終わりに1回だけ書く。
書く順は、探索の記憶、イベントログの最後の行、`report.json`である。
前の書き込みが失敗したら、後のものは書かない。
`report.json`と探索の記憶は、隣の一時ファイルに書いてから名前を変えて置き換える。
途中で止まっても、前の版が残るようにするためである。

| 項目 | 中身 |
|---|---|
| `schema` | 形式の版。1 |
| `mode` | 実行のモード。`explore`、`scenario`、`interview`のどれか |
| `started_at` | 開始の時刻。UTCで秒まで |
| `target` | 開始のURL |
| `reason` | 終了理由 |
| `stuck` | 行き詰まりの種類。`reason`が`stuck`のときだけ値を持つ |
| `usage` | 判断モデルを呼んだ回数、トークン数、コスト |
| `steps` | 操作の記録 |
| `calls` | 判断モデルの答えの記録 |
| `issues` | 見つけた問題 |
| `start_memory` | その実行が始めたときの探索の記憶 |

終了理由は次のとおり。

| `reason` | 意味 |
|---|---|
| `goal_achieved` | ゴールを達成した |
| `reported_done` | 判断モデルが終わったと答えた。達成は確かめていない |
| `stuck` | 行き詰まった。`stuck`は`declared`(判断モデルが答えた)か`no_progress`(進まない回数が閾値に達した) |
| `budget_exceeded` | 判断のステップの数の上限に達した。インタビューのモードでは1ステップで最大2回呼ぶ |
| `time_exceeded` | 実行の時間の上限に達した |
| `user_aborted` | 利用者が中断した |
| `judge_unavailable` | 判断モデルへの問い(1ステップの答え)が3回続けて失敗した。APIのエラー、タイムアウト、橋渡しの失敗を数える |

終了理由の決まり方は[中核の状態機械](core.md)にある。

### 操作の記録

`steps`には、ブラウザへの操作を順に1つずつ書く。

| 項目 | 中身 |
|---|---|
| `step` | ステップ番号 |
| `cause` | 誰の求めた操作か |
| `op` | 操作の名前 |
| `target` | 操作した要素の識別子。`role`、`name`、`nth`を持つ |
| `input` | 入力に使った`inputs`のキー |
| `p` | 判断モデルの確率 |
| `act_ms` | 操作にかかった時間 |
| `settle_ms` | 操作のあと、画面を読めるまでにかかった時間 |

`cause`は、判断モデルの提案なら`judge`である。
中核が自分で操作したときは、課金画面からの離脱が`paywall`、許可ドメインへの戻りが`outside`、固まった画面の読み直しが`frozen`になる。
`p`は、判断モデルの確率が無ければ0、中核が自分で行った操作なら1にする。
入力した値そのものは書かない。
`input`には、入力欄の名前が`inputs`のキーに一致したときだけ、そのキーを書く。
要素の識別子は[探索モード](explore-mode.md)にある。

### 判断モデルの答えの記録

`calls`には、判断モデルを呼ぶたびに1つずつ、呼んだ順に書く。
インタビューのモードは、操作を行うステップで2回呼ぶ(1回目は期待を除いた問い、2回目は期待の問い)。
その2件は同じ`step`を持つので、`calls`の数はステップの数より多くなりうる。
2回目の答えが使えなかったときは、`error`を`malformed`、`question`を`expectation`にして書く。
インタビューの実行は`webqa replay`に渡せないので、この記録の2件は再生に使わない。
インタビューのモードでは、試行をすべて終えたあとの問い(自然さの問い、目的のずれの問い)も`calls`に書く。
どのステップにも属さないので、`step`を0にする。
ステップ番号は1から数えるので、0はステップの問いと重ならない。

| 項目 | 中身 |
|---|---|
| `step` | ステップ番号。0は試行の後の問い |
| `think_ms` | 判断モデルが答えるまでの時間 |
| `answers` | 問いごとの選択肢と確率。失敗したときは`null` |
| `error` | 失敗の種類。答えたときは`null` |
| `question` | インタビューで足した問いの答えが使えなかったときの、その問いのid。そうでない失敗と、答えたときは`null` |
| `usage` | その回のトークン数。失敗したときは`null` |

`webqa replay`は、この記録を台本にして実行をやり直す([コマンド](cli.md))。
確率の無い選択肢は、確率を`null`で書き、再実行で確率の無い選択肢に戻す。
失敗の種類は[判断モデル](judge.md)にある。

### 問題の記録

`issues`には、見つけた問題を見つけた順に1つずつ書く。

| 項目 | 中身 |
|---|---|
| `step` | 見つけたステップ |
| `kind` | 問題の種類 |
| `class` | `confirmed`か`reference` |
| `evidence` | 問題の根拠になった画面の文字列。判断モデルが判定した種類では`null` |
| `label` | `semantic`の問題の名前。ほかの種類では`null` |
| `p` | 判断モデルの確率。中核やブラウザが判定した種類では`null` |
| `screenshot` | 実行のディレクトリからのパス。`screenshots/ISSUE_…png`のように`screenshots/`から書く。撮れなかったときは項目ごと省く |

### 計測とコスト

計測は、ステップごとに判断、操作、画面の変化を待つ時間を、注入した時計で測る。
コストは、判断モデルのトークン数と設定の単価から求める。
送ったトークン数と受け取ったトークン数をそれぞれ1000で割り、`judge.pricing`の単価を掛けて足す。

### 探索の記憶

`start_memory`には、その実行が始めたときの探索の記憶を、記憶のファイルと同じ形で書く。
再実行は、この記憶から始める([コマンド](cli.md))。
インタビューのモードの`report.json`では、`start_memory`を`null`にする。

## 書き込みの失敗

記録の書き込みに失敗したら、実行を止めて終了コード3で終わる。
ディスクがいっぱいのときなどが、これに当たる。
イベントログの書き込みが一度失敗したら、それより後の行は書かない。

## イベントログ

イベントログ`events.jsonl`は、1行に1つのJSONを書くJSONLである。
1行目は実行の開始で、形式の版と開始の時刻を持つ。
各行は、通し番号`seq`、開始からの経過時間`elapsed_ms`、ステップ番号`step`、種類`kind`、中身を持つ。
`step`は、ステップに属さない行では省く。

```json
{"seq":0,"elapsed_ms":0,"kind":"run_started","schema":1,"mode":"explore","started_at":"2026-10-18T02:00:00Z"}
{"seq":1,"elapsed_ms":1200,"step":1,"kind":"decided","op":"click","target":"保存","p":0.9}
{"seq":2,"elapsed_ms":2100,"step":1,"kind":"executed","changed":true,"accesses":1}
{"seq":9,"elapsed_ms":60000,"kind":"run_finished","reason":"goal_achieved"}
```

イベントの型は`webqa-core`の`event`に置き、CLIとTUIが同じ型を使う。
`webqa-core`は時刻の型を持たないので、各行の時刻は開始からの経過時間(ミリ秒)だけで表す。
開始の時刻は、CLIが文字列にして開始の行にだけ入れる。
各行の時刻が要るときは、開始の時刻と経過時間から求める。
CLIは1行書くたびにフラッシュする。

| `kind` | 中身 |
|---|---|
| `run_started` | 実行の開始。`schema`、`mode`、`started_at` |
| `memory_reset` | 探索の記憶のファイルが使えず、空の記憶から始めた。`cause`に理由 |
| `asked` | 判断モデルに1回問いを送った。呼び出しごとに1行書くので、インタビューのモードでは1つのステップに2行出ることがある。`input_tokens`、`output_tokens`、`think_ms` |
| `decided` | 判断モデルが操作を選んだ。`op`、`target`、`p` |
| `recovered` | 中核が自分で操作した。`op`と、操作の理由の`cause` |
| `executed` | ブラウザが操作した。画面が変わったかの`changed`と、ネットワークへのアクセスの数`accesses` |
| `rejected` | ガードレールが判断モデルの提案を止めた。`why`に理由 |
| `anomaly` | 判断モデルの答えが使えなかった。`cause`と、答えの誤っていた問い`question`。API のエラーなら、橋渡しが返した短い文`detail`(残せる文が無ければ省く) |
| `issue` | 問題を見つけた。`issue`、`class`、`evidence`、`label`、`p`、`screenshot` |
| `skipped` | ブラウザが何もしない操作だった。`cause`は`not_an_input`か`no_input_value` |
| `stage_advanced` | 決め打ちシナリオが次の段階に進んだ。0から数える`stage`と、名前の`name` |
| `waited` | 時間窓が空くまで待った。待ち終わる時刻の`until_ms` |
| `trial_started` | インタビューの試行が始まった。1から数える`trial` |
| `trial_finished` | インタビューの試行が終わった。`trial`と、終わり方の`ending` |
| `run_finished` | 実行の終わり。`reason`と、行き詰まったときの`stuck` |

`rejected`の理由は[安全のための仕組み](safety.md)にある。
`memory_reset`の理由は[探索モード](explore-mode.md)にある。

インタビューのモードは、1回の実行のイベントを1つの`events.jsonl`に書く。
試行の区切りは、`trial_started`と`trial_finished`の行で示す。
試行の中のステップ番号は、試行ごとに1から数え直す。
`ending`は、`goal_met`、`done`、`gave_up`、`no_progress`、`budget_spent`、`time_up`、`interrupted`のどれかである。
`budget_spent`の試行は試行の数Nに入るが、目的に届かない課題は出さない。

```json
{"seq":1,"elapsed_ms":0,"kind":"trial_started","trial":1}
{"seq":9,"elapsed_ms":84000,"kind":"trial_finished","trial":1,"ending":"done"}
```

## watchの画面

`watch`の画面は、`webqa watch <実行のディレクトリ>`で起動する。
実行ループとは別のプロセスで動き、イベントログを読むだけで、実行の状態は変えない。
実行の機能はすべてCLIのサブコマンドで満たし、`watch`の画面は表示だけを受け持つ。

`watch`の画面は、注入した時計で200ミリ秒ごとに、読む、描く、待つを繰り返す。
前回読んだ位置から先だけを読み、改行で終わっていない最後の行は次の回に回す。
ファイルの変更通知は使わない。
一定の間隔で読み直せば足りるからである。
`events.jsonl`がまだ無いときは、空のファイルとして読み、現れるまで待つ。
読めなかった回は、次の回に読み直す。

画面の状態は、イベントを1行ずつ畳み込む純粋な関数で更新する。
画面の1行目には、モード、実行中か終わったか(終わったら終了理由)、経過時間を出す。
その下の左の枠「進み具合」には、インタビューの試行とそのうち終わった数、シナリオの段階、今のステップを出す。
同じ枠に数も並べる。
判断、画面が変わったステップ、ガードレールが止めた提案、使えなかった応答、中核の回復の操作、見つけた課題、通信、トークンの送受信の数である。
右の枠「直近の操作」には、新しい順に最後の8つの操作を出す。
判断モデルが選んだ操作の1行は、ステップ、操作と要素と確信度、その結果(変わった、変わらない)である。
結果が出るまでは`…`を出す。
中核の回復の操作は、`回復`と操作の名前の1行にする。
ガードレールが止めた提案は、`提案`と止めた理由の1行にする。
止めた提案にはイベントログに`decided`の行が無いので、操作の名前は出せない。
結果は色で分ける。
画面の幅が70桁より狭いときは、2つの枠を上下に並べる。
最下行には、閉じるキー(Ctrl-C)を出す。
判断予算などの上限は設定にあり、イベントログに無いので出さない。
状態が変わった回だけ描き直す。

端末はrawモードにしない。
描くときは画面を消し、端末の大きさの領域に1画面を書く。
大きさを読めないとき(制御端末が無いときなど)は、80×24で描く。
`run_finished`を読んだら、読むのをやめて最後の画面を残す。

`watch`の画面で受ける操作は、終了だけである。
終了はCtrl-Cで受け、終了コード0で終わる。
rawモードにしないので、キーを読む処理は持たない。
実行のディレクトリが無ければ、標準エラーに`実行のディレクトリが無い`と書き、終了コード2で終わる。

`watch`の画面のコードは`webqa-tui`に置く。
同じcrateには、`webqa ledger`で開くインタビューの台帳の画面もある。
台帳の画面は、`watch`の画面と違ってキーを読み、選んだ結果を台帳のファイルに書き戻す。
書き戻すのは、`ledger.md`の課題のチェックボックスだけである。
イベントログと実行結果には書かない。
キーの割り当てと書き戻しの扱いは、[インタビューのモード](interview-mode.md)の「選ぶこと」にある。
描画は、ratatuiのテスト用の端末でゴールデンテストにする([テストの層](testing.md))。
