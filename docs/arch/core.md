# 中核の状態機械

`webqa-core`の`machine`は、1回の実行の状態遷移を受け持つ。
中核は純粋で、副作用を持たない。
実行ループが中核の返す効果を実行し、その結果と経過時間を中核へ返す。
全体の中での位置は[overview.md](overview.md)にある。

## 状態の持ち方

状態は`State`に持つ。
主な項目は次のとおり。

| 項目 | 中身 |
|---|---|
| `phase` | 今の状態(下の「状態遷移の概略」の8つ) |
| `last` | 直前の観測`Seen` |
| `memory` | 探索の記憶`Memory`(画面ごとのグラフ) |
| `at`、`origin` | 直前の観測と開始の画面が、記憶のどの画面に当たるか |
| `shown` | 画面ごとに、表示領域に現れたことのある要素 |
| `counters` | 固まりと行き詰まりの回数`Counters` |
| `budget` | 判断予算`Budget { used, cap }` |
| `window` | 時間窓`RequestWindow` |
| `outside` | 直前の観測が許可ドメインの外にあるか |
| `proposal` | 判断モデルの答えから、操作を観測するまで持つ提案`Proposal` |
| `notes` | 中核が記録したこと(止めた提案、応答の異常、問題)。増えるだけである |
| `stage` | 決め打ちシナリオの今の段階の番号。0から数える |
| `unmoved` | 直前に操作して画面が変わらなかった要素 |
| `failing` | 判断モデルへの問い(1ステップの答え)が続けて失敗した回数 |

判断予算は残りを持たず、使った数と上限から残りを導く。
こうすると、残りと使った数の和は必ず上限に等しい。

課金画面か、要素がまだあるか、画面が変わったか、done_whenを満たしたかは、状態に持たない。
中核は観測からその都度判定する。
制限時間に達したかも持たず、渡された経過時間と設定の上限から判定する。
実行のモードは、設定の値から作る`Rules`の`mode`が持つ。

## 状態遷移の概略

状態遷移の図は、ommの`state-transitions`にある。
図は`just omm view`で開く。
状態は次の8つで、図の名前と`Phase`の腕の名前は同じである。

| 状態 | 中身 |
|---|---|
| `Idle`(待機) | 優先順位の表を調べる |
| `Awaiting`(判断待ち) | 判断モデルの答えを待つ |
| `Confirming`(確認中) | 実行直前の要素の取り直しを待つ |
| `Acting`(実行) | ブラウザの操作か、課金画面からの離脱のあとの観測を待つ |
| `Returning`(移動中) | `return`のあとの観測を待つ |
| `Recovering`(復旧) | 再読み込みのあとの観測を待つ |
| `Sleeping`(窓待ち) | 時間窓が明けるのを待つ |
| `Ended`(終了) | 実行が終わった |

待機の状態は、中核が表を調べている間にだけ現れる。
実行ループが受け取る状態は、待機以外のどれかである。

ツールの利用者による中断は、状態機械の外から実行ループが受け取る。
実行ループは`machine::abort`を呼び、終了理由を「利用者による中断」にする。
すでに終わった状態なら、元の終了理由のまま返す。
記録の書き方は[runtime.md](runtime.md)にある。

終了理由の`error`は、実行ループが付け、中核は作らない。
ブラウザの操作に失敗したとき、実行ループは失敗の前の状態から記録を書き、終了理由を`error`にする。

## アクションの表

遷移は、静的な表の行として書く。
1行は、有効になる条件の関数と、遷移の関数の組である。

```rust
pub(super) type Fire = fn(State, &Now) -> Next;

pub(super) struct Action {
    pub(super) enabled: fn(&State, &Now) -> bool,
    pub(super) fire: Fire,
}

pub enum Step {
    Continue(Box<State>, Effect),
    Finished(Outcome),
}

pub(super) enum Next {
    Go(Box<State>),
    Out(Step),
}
```

`Now`は、その回の`Facts`と、実行の開始からの経過時間を持つ。
`Step`は実行ループへ返す値で、`Next`は1行の遷移の結果を表す。

表は3つの部分を順に並べる。

1. 終わった状態は、終わったままにする行。
2. 待機の行。
3. 判断待ち、確認中、実行、移動中、復旧で、効果の結果を受ける5行。

`machine::step`は、最初に有効になった行を実行する。
結果が`Next::Go`なら、同じ`Facts`のまま表を調べ直す。
`Next::Out`が出たら、その`Step`を実行ループへ返す。
外に効果を頼まない行は`Next::Go`を返す。
段階を進める行、提案を止める行、応答の異常の行、確認中の中止の行、観測を受ける行がそうである。
そのため、実行ループが受け取る`Step::Continue`は必ず効果を持つ。

`Next::Go`を返す行は、状態を待機へ戻すか、段階の番号を進める。
待機の行が`Next::Go`を返すのは段階を進めるときだけなので、調べ直す回数には上限がある。

状態に合わない`Facts`が来たときは、ほかを変えずに待機へ戻す。
窓待ちには専用の行が無く、目覚めた結果はこの扱いで待機へ戻る。

### 待機中の優先順位

待機の行は、まず状態から`plan::Waiting`を作る。
`Waiting`は、ゴール、終了の条件、待つか直すかの条件を真偽で持つ。
`plan::choose`は、優先順位の表を上から調べ、最初に条件が成り立った行を選ぶ。

| 段 | 待機中に選ぶ行 | 外に頼む効果 |
|---|---|---|
| 1 | 最後でない段階のdone_whenを満たした → 次の段階へ進む | なし |
| 1 | ゴールを満たした → ゴール達成で終了 | なし |
| 2 | 行き詰まりの回数が閾値に届いた → 行き詰まりで終了 | なし |
| 3 | 判断モデルの失敗が3回続いた → 判断モデルの停止で終了 | なし |
| 3 | 判断予算切れ → 判断予算切れで終了 | なし |
| 3 | 制限時間に達した → 時間切れで終了 | なし |
| 4 | 時間窓の上限に達している → 窓が明けるまで待つ | 待機 |
| 4 | 固まりの回数が閾値に届いた → ページを開き直す | 再読み込み |
| 4 | 許可ドメインの外 → 許可ドメインへ戻る | `return`(開始のURLを開き直す) |
| 4 | 課金画面 → 設定の離脱操作をする | 離脱の操作 |
| 5 | 判断モデルに問い合わせる | 問い合わせ |

表の「段」は優先順位の段である。
各行の条件は、上の段の条件が成り立たないことも確かめる。
上の段の否定は、`going_on`、`running`、`active`、`open`のような名前の付いた述語にする。
述語は、1つ上の段の述語に、その段の条件の否定を足して作る。
`active`は、判断予算と制限時間の2つの条件を`in_time`にまとめ、判断モデルの停止を足した`served`を足す。
そのため、段をまたいで行を並べ替えても、選ぶ行は変わらない。
同じ段の中では、表の並びが先の行を選ぶ。

1段目のゴールは、モードで変わる。
決め打ちシナリオでは、今の段階のdone_whenを満たしたことである。
探索モードでは、判断モデルに1回以上問い合わせたうえで、開始の画面から未操作の要素へたどれなくなったことである。
それぞれ[scenario-mode.md](scenario-mode.md)と[explore-mode.md](explore-mode.md)にある。

3段目では、判断モデルの停止を最初に選ぶ。
予算の最後の1回で3回目の失敗が出たら、判断予算切れでなく判断モデルの停止で終わる。
判断モデルに届かないまま終わったことを、予算を使い切ったことと見分けるためである。

4段目では、時間窓を待つ行を最初に選ぶ。
上限に達している間は、開き直し、戻り、離脱も窓が明けるまで待つためである。
窓待ちで眠るのは、次の窓の始まりと制限時間のうち、早いほうまでである。

問い合わせの行は、判断予算を1つ使う。
選ばれた行の遷移は、`Pick`の値と遷移の関数を組にした表`MOVES`から引く。

### 判断待ち以降の行

| 起点 | 行 | 外に頼む効果 |
|---|---|---|
| 判断待ち | 応答の異常 → 記録して待機へ戻る | なし |
| 判断待ち | ガードレールで止める → 記録して待機へ戻る | なし |
| 判断待ち | done → 未検証の終了 | なし |
| 判断待ち | stuck → 行き詰まりで終了 | なし |
| 判断待ち | 要素への操作を通す → 確認中へ | 実行直前の要素の取り直し |
| 判断待ち | 要素を対象にしない操作を通す → 実行へ | ブラウザの操作 |
| 確認中 | 要素が無い、または差し替わった → 記録して待機へ戻る | なし |
| 確認中 | 同じ要素がある → 実行へ | ブラウザの操作 |
| 実行 | 操作のあとの観測を受け、カウンタを更新する → 待機へ戻る | なし |
| 移動中 | 戻ったあとの観測を受ける → 待機へ戻る | なし |
| 復旧 | 開き直したあとの観測を受ける → 待機へ戻る | なし |

判断待ちで止める提案は、次の3つである。
禁止要素への操作、取り直すための参照が無い要素への操作、確信度の低い`back`である。
確認中では、問い合わせたときと同じDOMノードがあるかを確かめる。
判定の中身は[safety.md](safety.md)にある。

課金画面だけは、問い合わせの前に待機の4段目で判定する。
離脱も提案として持ち、実行の状態を通って観測を受ける。

ブラウザの操作を頼む行は、時間窓のアクセスを1回使う。
問い合わせと要素の取り直しは、時間窓に数えない。

観測を受ける行は、観測を状態に入れてから待機へ戻る。
待機へ戻ったあとは、同じ`Facts`のまま優先順位を上から調べる。
待機の行が読む画面は、状態に入れた直前の観測である。
そのため、離脱のあとで行き詰まりの回数が閾値に届けば、同じ`machine::step`の中で行き詰まりとして終わる。

## カウンタ

カウンタは、実行の状態で観測を受ける行で更新する。
課金画面からの離脱も実行の状態を通るので、ここで数える。

| 観測の結果 | 固まりの回数 | 行き詰まりの回数 |
|---|---|---|
| 画面が変化しなかった | 1増やす | 下の2行に当たらなければ1増やす |
| 画面が変化した | 0に戻す | 下の2行に当たらなければ1増やす |
| 未操作の要素を操作した | 上の2行による | 0に戻す |
| スクロールで未操作の要素が新しく見えた | 上の2行による | 0に戻す。インタビューのモードでは戻さない |

インタビューのモードでは、スクロールで新しく見えた要素を進展に数えない。
ペルソナがスクロールを続けるだけなら、閾値の回数で行き詰まりとして終わる。
モードは規則の`mode`で見分ける。
許可ドメインの外に出たときは、画面が変化したとみなす。
課金画面からの離脱は、操作済みの要素を増やさない。
そのため、離脱のたびに行き詰まりの回数が1増える。
課金画面が消えないままなら、閾値の回数で行き詰まりとして終わる。

開き直すときは、固まりの回数を0に戻し、行き詰まりの回数は変えない。
段階を進めたら、どちらの回数も0に戻す。
判断予算、時間窓、探索の記憶は、段階を進めても戻さない。
ガードレールで止めた提案、応答の異常、確認中の中止では、どちらの回数も変えない。
この3つでも、問い合わせた時点で判断予算を1回使っている。
ただしインタビューのモードでは、止めた提案と確認中の中止で、行き詰まりの回数を1増やす。
固まりの回数は変えない。
止められた提案が続くと、画面が変わらないまま同じ問いに同じ答えが返り、判断予算を使い切るためである。
確認中の中止のあとの観測が許可ドメインの外でも、外に着いた分と合わせて1だけ増やす。
行き詰まりの閾値は、進展の無いステップの数だからである。

判断モデルの失敗の回数は、判断待ちで答えを受ける行で更新する。
数えるのは、中核が受け取る1ステップの答えで、判断モデルを呼んだ回数ではない。
インタビューのモードは1ステップで判断モデルを2回まで呼ぶが、どちらかが失敗すれば、そのステップの答えを1回の失敗と数える。
APIのエラー、タイムアウト、橋渡しの失敗なら1増やす。
ほかの答えなら0に戻す。
形の崩れた答え、インタビューで足した問いの使えない答え、`replay`の台本切れも0に戻す。
これらは判断モデルに届いているか、判断モデルの外の事情だからである。
閾値は3で固定し、設定の項目は設けない。
回線が切れたときに、判断予算を使い切るまで失敗を繰り返さないためである。

戻ったあとや開き直したあとの観測が、まだ許可ドメインの外にあることがある。
許可ドメインの外にいるこのときだけは、行き詰まりの回数を1増やし、固まりの回数は変えない。
確認中に要素が無かったときの観測も同じ扱いにする。
外へ送り返し続けるページで、`return`を限りなく繰り返さないためである。

## 1ステップの流れ

実行ループは、中核が返す効果を実行し、その結果を次の`Facts`にして中核へ返す。
実行ループは`webqa`の`run`にある。

```rust
loop {
    match step {
        Step::Continue(state, effect) => {
            let kept = (*state).clone();
            tokio::select! {
                biased;
                () = interrupt.wait() => return Ok(machine::abort(kept)),
                next = advance(*state, effect, ports) => step = next?,
            }
        }
        Step::Finished(outcome) => return Ok(outcome),
    }
}
```

`advance`は`perform`で効果を実行し、`machine::step`に`Facts`と経過時間を渡す。
時刻は`Facts`に入れず、`machine::step`の3つ目の引数で渡す。
状態と観測は大きいので、`Step::Continue`と`Facts::Page`は`Box`で持つ。

| 効果 | `Facts`に入るもの | 受ける行 |
|---|---|---|
| 問い合わせ | 判断モデルの答えか、応答の失敗 | 判断待ち |
| 実行直前の要素の取り直し | 取り直した観測`Seen` | 確認中 |
| ブラウザの操作、離脱 | 操作のあとの観測`Seen` | 実行 |
| `return` | 戻ったあとの観測`Seen` | 移動中 |
| 再読み込み | 開き直したあとの観測`Seen` | 復旧 |
| 待機 | 目覚めたことだけ | (待機へ戻る) |

`Facts`は2つの腕を持つ。
`Facts::Outside`は問い合わせの答えか目覚めたことで、`Facts::Page`は観測である。

観測`Seen`は、次のものを持つ。

- 伏せ字を通した画面`Screen`(ページの操作可能要素とURL。表示領域の中の要素は`visible()`で絞る)
- 表示領域の大きさ
- ガードレールの材料(課金画面の材料、要素の候補、DOMノードの参照)
- done_whenが読むページ全体の要素とテキスト

ガードレールの材料は、伏せ字を通す前の値から集める。
判定の材料を集めるのはアダプタで、判定するのは中核である。

## 効果の振り分け

効果は、腕2本ずつの入れ子の列挙型にする。
1つの`match`の腕を減らし、複雑度の上限に収めるためである。

```rust
pub enum Effect { Outside(Outside), Page(PageEffect) }
pub enum Outside { Ask(Questions), Sleep(Wake) }
pub enum PageEffect { Look(Target), Touch(Touch) }
```

`Touch`は、ブラウザの操作、離脱、再読み込み、`return`をまとめた構造体である。
操作の種類は名前の文字列で持ち、対象の要素と確信度を添える。
中核が自分で頼む操作(再読み込み、`return`、離脱)は、確信度を1にし、要素を持たない。
どのPlaywrightの呼び出しにするかは、`webqa-browser`の中の表で引く。
実行ループの`perform`は、入れ子の各層で腕2本の`match`を書き、層ごとに関数を分ける。

## 仕様との対応

TLA+の仕様は`tasks/loopeng/WebExploratoryQA.tla`にある。
仕様のアクションと実装の行の対応は次のとおり。

| 仕様のアクション | 実装の行 | ずれ |
|---|---|---|
| `RequestDecision` | 待機の5段目と、判断待ちで答えを受ける行 | 時間窓に数えない。課金画面の観測を含まない |
| `ApplyGuardrails` | 判断待ちの行と、確認中の2行 | 課金画面の判定は待機の4段目にある。要素の存在と同一性は確認中で確かめる |
| `ExecuteNoChange`、`ExecuteChange`、`ExecuteOutOfDomain` | 実行で観測を受ける1行 | 3つの結果を観測で分け、1行にまとめた |
| `FinishByProposalDone`、`FinishByProposalStuck` | 判断待ちのdoneとstuckの行 | 実行の状態を通らずに終わる |
| `ReturnToAllowedDomain` | 待機の4段目の戻る行と、移動中で観測を受ける行 | 時間窓に数える。戻った先が外なら行き詰まりの回数を増やす |
| `RecoverFromFreeze`、`ResumeAfterRecovery` | 待機の4段目の開き直す行と、復旧で観測を受ける行 | 時間窓に数える |
| `ResetRequestWindow` | 行にしない。窓の番号を経過時間から求める | 上限の間は窓待ちの行で待つ |
| `FinishNormally` | 待機の1段目のゴール達成の行 | なし |
| `FinishStuck` | 待機の2段目 | スクロールで新しく見えた要素でも数え直す。インタビューのモードでは数え直さない |
| `ExceedDecisionBudget` | 待機の3段目 | なし |
| `FinishTimeUp` | 待機の3段目 | 判断予算切れと同じ段に置く |
| (なし) | 待機の3段目の、判断モデルの停止で終える行 | 判断モデルの失敗の連続を仕様はまだ持たない |
| `AdvanceStage` | 待機の1段目の、次の段階へ進む行 | なし |
| `TimeElapses` | 行にしない。渡された経過時間が制限時間に達したかで判定する | なし |
| `UserAbort` | `machine::abort` | 記録を書いてから終わる処理は実行ループが受け持つ |
| (なし) | 待機の4段目の離脱する行。そのあとは実行の状態を通る | 課金画面を問い合わせの前に判定する |
| (なし) | 実行ループ | ブラウザの操作の失敗で、終了理由`error`を付ける。中核の遷移の外にある |

仕様では、許可ドメインへ戻る操作は必ず中へ着く。
実装では`return`のあとも外にいることがあり、そのときは判断を経ずに行き詰まりの回数が増える。
そのため、この場合に限り、カウンタが判断の数を超えないという仕様の性質は成り立たないことがある。

## 決定的なテスト

中核は純粋なので、小さな定数を与えれば全状態を探索できる。
テストは`crates/webqa-core/tests/exhaustive.rs`にある。
開始の画面から、状態に合う`Facts`と後の時刻を有限の候補から選び、幅優先で総当たりする。
探索は4つある。
段階の無い決め打ちシナリオ、段階のある決め打ちシナリオ、探索モード、段階の無いインタビューである。

候補は次のように絞る。

- 時刻は、同じ窓の中、次の窓の始まり、制限時間の後、の3つにする。
- 画面は、安全な要素と禁止要素から作った数枚の合成の画面にする。
  課金画面、許可ドメインの外の画面、要素が0件の画面、要素が差し替わった画面も入れる。
- 答えは、操作の種類、確信度の高低、要素の番号(存在しない番号を含む)の組にする。
  選択肢に無い操作の種類も入れる。
  判断モデルの答えが尽きた失敗と、APIのエラーも入れる。
- 閾値、予算、窓の上限は小さな値にする。

到達したすべての遷移で、次の性質を確かめる。

- 終わった実行は終わったままである。
- 禁止要素への操作と、確信度の低い`back`は実行しない。
- 禁止要素のある画面では`enter`を押さない。
- 固まり、許可ドメインの外、課金画面の間は問い合わせない。
- 判断予算と時間窓は上限を超えない。
- 判断モデルの失敗の回数は閾値を超えず、答えが届けば0に戻る。
- 終了理由は、状態の値で裏づけられる。
- 判断予算切れと時間切れが同時に起きても、終了理由は1つである。
- 探索の記憶と記録は増えるだけである。
- 待機中は優先順位どおりの行を選ぶ。
- 探索モードのゴール達成には、1回以上の問い合わせが要る。

表のすべての行に到達したことも確かめる。
乱数を使わないので、テストは毎回同じ結果になる。
テストの層の全体は[testing.md](testing.md)にある。
