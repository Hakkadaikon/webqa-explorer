# 品質ゲートの下での書き方

品質ゲートは、関数ごとの複雑度に厳しい上限を置く。
この文書は、その上限に収まるコードの書き方の決まりをまとめる。
上限の値と検査の道具は[quality-gates.md](../quality-gates.md)にある。

## 複雑度の数え方

`rust-code-analysis`は、次のものを1つにつき循環的複雑度+1と数える。

- `match`の腕(腕4本で5、腕5本で6)
- `if`、`while`、`for`
- `?`
- `&&`と`||`

クロージャの中の分岐は、外側の関数の合計に入る。
関数ごとの上限は5なので、腕5本の`match`だけで超える。
`matches!`のようなマクロの中身は数えられないが、これに頼らない。
ネストの深さは、clippyの`excessive-nesting-threshold = 3`でも止まる。

## 決まり

5通り以上の場合分けは、静的な表かtraitで書く。
表の1行には、場合を見分ける値と、その場合の性質や関数を持たせる。
探す処理は`iter().find(...)`の1つで済み、場合が増えても行が増えるだけになる。
中核の遷移の表、待機中の優先順位、ブラウザの操作の表が、この形である。
例は[core.md](core.md)にある。

`match`は腕4本までにする。
`A | B`のように腕をまとめるか、種類の近いものを入れ子の型に分ける。
効果の型`Effect`は、腕2本ずつの入れ子にしてある。

条件は、名前の付いた小さな述語に分ける。
1つの式に`&&`と`||`を並べない。
長い条件は、1つ前の述語に条件を1つ足した述語を重ねて作る。

列挙型と文字列の変換は、serdeのderiveで書く。
手書きの`match`にしない。

1つの関数で使う`?`は4つまでにする。
`rust-code-analysis`は`?`を関数の出口に数え、`scripts/metrics.py`は出口の数を4までに抑えるためである。
手順の長い処理は、`?`を1つずつ持つ小さな関数に分ける。

`as`での変換、添字での参照、`unwrap`は使わない。
clippyの`as_conversions`、`indexing_slicing`、`unwrap_used`が止める。
表は`get`や`find`で引き、見つからないときの値を決めておく。

`mod.rs`は使わない。
`guard.rs`と`guard/`のように、ファイルとディレクトリを並べる。

## ファイルの分け方

ファイルごとにもHalsteadの上限があるので、1ファイルは1つの話題に絞る。
単体テストは本体と同じファイルに書かず、`guard/tests.rs`のような隣のファイルに置く。
本体からは`#[cfg(test)] mod tests;`で読み込む。
テストが大きくなったら、`explore/graph/tests/`のように話題ごとのファイルに分ける。
