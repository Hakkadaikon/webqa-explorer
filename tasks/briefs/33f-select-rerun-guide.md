## 受け持つシナリオ

### 課題を選ぶことと TUI(7本)

- Markdown のチェックボックスを直接書き換えて選んだ課題は、選んだ課題として読み戻せる
- TUI で課題の選択を付け外しすると、同じ Markdown に書き戻す
- TUI で書き戻しても、選択のほかの中身は変えない
- TUI で開いたあとに台帳が外で書き換えられていたら、上書きせずに知らせる
- TUI で課題を種類で絞り込める
- TUI で課題を選ぶと、その中身を読める
- 実行中のイベントログを追う画面は、今のまま使える

### 再実行と照らし合わせ(11本)

- 前回も今回も出た課題は、残っているとして示す
- 今回だけ出た課題は、新しく出たとして示す
- その画面に届いた試行の数が前回以上で、1回も起きなければ、解消したとして示す
- その画面に届いた試行の数が前回より1少なければ、1回も起きなくても解消したとせず、確かめられなかったとして示す
- 前回課題が出た画面に届かなければ、確かめられなかったとして示す
- 前回選んだ課題が残っていれば、選択を引き継ぐ
- 新しく出た課題は、選ばれていない状態で台帳に出す
- 前回の台帳を渡さなければ、すべての課題を新しく出たとして示す
- 前回の台帳が決まった書式で読めなければ、照らし合わせずに設定エラーにする
- 前回の台帳のペルソナか目的が今回と違えば、照らし合わせずに設定エラーにする
- 目的を推測させた実行どうしは、推測した文が違っても、開始の URL が同じなら照らし合わせる

### 手引きと形式の検査(5本)

- 形式の検査のサブコマンドは、正しい文書を通す
- 形式の検査のサブコマンドは、誤りのある文書の誤りの場所を示して失敗する
- 手引きは Agent Skills の標準の形式で、形式の検査のサブコマンドを呼ぶ手順と書式の例を持つ
- 手引きは、目的の done_when を確定の操作ができる画面まで来たことで書くよう示す
- 手引きは、このリポジトリの開発用の手順書とは別の場所に置く

名前は、Rule のファイルの `READY` に入れる。

## 書く手順の文言

この Rule にだけ出る文言を書く。`{string}` は引用符の値、`{n}` は数(Examples の値に合わせて `{int}` か `{float}`)、`<p>` は Examples の列。共通の文言は 33a の `common.rs` にあるので書かない。

### 課題を選ぶことと TUI

- 台帳の課題 {string} のチェックボックスを、エディタで付ける
- 選んだ課題は {string} だけである
- 終わった実行の台帳を TUI で開いている
- 課題 {string} の選択を付ける
- 同じ台帳のファイルで、{string} のチェックボックスが付いている
- 課題 {string} の選択を付け、また外す
- 台帳のファイルの中身は、開く前と同じである
- そのあとに、エディタで台帳の課題 {string} のチェックボックスを付けて保存している
- TUI で課題 {string} の選択を付ける
- 台帳のファイルは上書きされておらず、{string} のチェックボックスは付いたままである
- TUI に、台帳が外で書き換えられたことが表示されている
- 判断に迷う課題が2件、視認性が悪い課題が1件ある台帳を TUI で開いている
- 種類を視認性が悪いに絞る
- 一覧には視認性が悪い課題1件だけが出ている
- 台帳を TUI で開いている
- 一覧から課題 {string} を開く
- {string} の直す指示の文、操作の列、ペルソナの性質、理由と期待が表示されている
- 探索モードの実行が動いている
- webqa watch でその実行を開く
- 実行中のイベントログを追う画面が、これまでどおり表示される

### 再実行と照らし合わせ

- 前回の台帳に課題 {string} がある
- 同じペルソナと目的で前回の台帳を渡して再実行し、{string} がまた出る
- 今回の台帳で {string} は残っているとして示されている
- 前回の台帳に課題 {string} が無い
- 同じペルソナと目的で前回の台帳を渡して再実行し、{string} が出る
- 今回の台帳で {string} は新しく出たとして示されている
- 前回の台帳に、<p> 回の試行のうち <p> 回が画面 {string} に届いて出た課題 {string} がある
- 前回の台帳を渡して <p> 回試し、そのうち <p> 回が {string} に届き、{string} は1回も起きない
- 今回の台帳で {string} は解消したとして示されている
- 前回の台帳に、3回の試行のうち2回が画面 {string} に届いて出た課題 {string} がある
- 前回の台帳を渡して3回試し、そのうち1回だけが {string} に届き、{string} は1回も起きない
- 今回の台帳で {string} は解消したとされず、確かめられなかったとして示されている
- 前回の台帳に、画面 {string} に出た課題 {string} がある
- 前回の台帳を渡して再実行し、どの試行も {string} に届かない
- 今回の台帳で {string} は確かめられなかったとして示されている
- {string} は解消したとされていない
- 前回の台帳で課題 {string} を選んでいる
- 前回の台帳を渡して再実行し、{string} がまた出る
- 今回の台帳で {string} は選ばれている
- 前回の台帳を渡して再実行し、新しい課題 {string} が出る
- 今回の台帳で {string} は選ばれていない
- 前回の台帳を渡していない
- インタビューのモードで実行し、課題が2件出る
- 今回の台帳の2件の課題は、どちらも新しく出たとして示されている
- 前回の台帳として渡したファイルの課題の区切りが崩れていて、読み戻せない
- 前回の台帳を渡して再実行しようとする
- 試行は始まっていない
- 前回の台帳の <p> が今回の設定と違う
- 前回の台帳は、目的を推測させた実行のもので、推測した文は {string} である
- 同じ開始の URL で目的を推測させて再実行し、推測した文が {string} になる
- 前回の台帳と課題の番号で照らし合わせている
- 推測した文の違いは、照らし合わせの結果にも設定エラーにもなっていない

### 手引きと形式の検査

- 決まった形式で書いた <p> がある
- 形式の検査のサブコマンドでその文書を検査する
- 検査は成功し、終了コードは {n} である
- <p> のある文書がある
- 検査は失敗し、終了コードは {n} である
- 誤りのある項目の名前が表示されている
- 配布物の中の、ペルソナと目的を書かせる手引きを読む
- 手引きは Agent Skills の標準の形式の前付けを持つ
- 手引きに、インタビューのメモや分析のデータから項目を埋める手順と、書式の例がある
- 手引きに、書いた文書を形式の検査のサブコマンドで確かめる手順がある
- 手引きに、目的の done_when は確定の操作ができる画面まで来たことで書く、という書き方と例がある
- 配布物の中の、ペルソナと目的を書かせる手引きの場所を見る
- 手引きは、このリポジトリの開発用の手順書の置き場の外にある

`{string}`、`{int}`、`{float}` 以外の広いパラメータと正規表現は使わない。Examples の値で手順を分ける必要があるときは、値から場面への対応表で引く。手順の中に `if` を書かない。

## 場面の組み立てと使う製品の口

- 始める前に main を取り込む。台帳の画面(#27、`webqa_tui::ledger` と `webqa_tui::ledger_file`)が入っていることを確かめる。
- 課題を選ぶことと TUI は、`webqa_tui::ledger::Screen` に入力を畳み込み、`ledger_file` で書き戻した台帳を読み戻して確かめる。キーを読む繰り返しは範囲の外(#27 の決定)なので、入力の値を手順で直接渡す。
- 再実行と照らし合わせは、前回の台帳を場面に置き、`webqa_core::interview::compare::compare` と、前回の台帳の頭の確かめ(`check_previous`、合わなければ設定エラーで終了コード2)を確かめる。
- 手引きと形式の検査は、形式の検査を `webqa::cli::check::app`(`check-docs`)で呼び、終了コードと誤りの項目の名前を確かめる。文書は `crates/webqa/tests/fixtures/docs/` を使う。手引きの3本は、#32 の `share/skills/` の手引きを読む。#32 が入っていなければ、この3本は後から足す。
- 最後に、`READY` の名前の数が feature の見出しの数(131)と一致することを確かめる assert を、`interview_acceptance.rs` の土台の確かめに足す(`33-plan.md` の親に決めてほしいこと3)。

## 注意

- 壊れたときに止まり続けるテストを書かない。`tokio::time` はこのクレートで禁止なので、待つなら std の `recv_timeout` か `tests/support/stuck.rs` を使う。
- シナリオを通すために Then の確かめを緩めない。Given の場面を feature と違うものにしない。親のまとめてのレビューは、何も確かめずに通るシナリオを must として探す。
- 期待値は値ごと比べる。Debug の文字列や部分一致で済ませない。
