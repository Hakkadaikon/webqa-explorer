## 受け持つシナリオ

### 課題の見つけ方(12本)

- 迷いの度合いが閾値以上なら、判断に迷う課題の手がかりにする
- 確信度が閾値に届かない操作を選んだら、判断に迷う課題の手がかりにする
- 引き返したら、判断に迷う課題の手がかりにする
- 同じ画面を行き来したら、行き詰まりとは別に迷いの手がかりとして記録する
- 同じ画面を行き来しても、試行は行き詰まりで終わらずに続く
- 判断モデルが見えにくい要素を挙げたら、視認性が悪い課題として記録する
- 判断モデルが見えにくい要素を挙げなければ、視認性が悪い課題は出さない
- 目的に届かなかった試行は、止まった画面と理由を目的に届かない課題として記録する
- 橋渡しが画像を扱えないと申告したら、視認性が悪い課題を出さず、そのことを台帳に書く
- 橋渡しが画像を扱えないと申告したら、問い合わせにスクリーンショットを含めない
- 橋渡しが画像を扱えないと申告したら、見えにくい要素の答えが無くても応答の異常にしない
- 橋渡しが画像を扱えると申告したのに見えにくい要素の答えが無ければ、応答の異常として扱う

### 台帳の書式(16本)

- 台帳は Markdown の1ファイルで、各課題は直す指示の文を1行目に持つ
- 各課題は、決まった項目をすべて持つ
- 課題をソースコードの場所に結び付けず、画面の要素の手がかりまでを書く
- 3回のうち1回だけ起きた課題も、その回数を添えて台帳に出す
- 課題は起きた割合の高い順に並べる
- 起きた割合が同じ課題は、課題の番号の順に並べる
- 同じ画面の同じ要素の同じ種類の課題は、実行をまたいで同じ番号になる
- 画面、要素、種類のどれかが違えば、別の番号になる
- 要素を持たない課題は、画面と種類で番号を決める
- スクリーンショットの名前は、課題の番号・試行の番号・ステップの番号から作り、パスの区切りを含めない
- 台帳を読み戻すと、書いた課題の項目と選択がそのまま戻る
- 判断モデルの自由な文に台帳の書式が入っていても、台帳の構造を崩さない
- 判断モデルの自由な文に改行が入っていても、直す指示の文は1行のままにする
- 台帳に書く文にも、設定で指定した機密情報の伏せ字を通す
- 台帳に、ペルソナの名前、目的、開始の URL、終えた試行の回数を書く
- インタビューの課題だけを見つけて終わったら、終了コードは0になる

名前は、Rule のファイルの `READY` に入れる。

## 書く手順の文言

この Rule にだけ出る文言を書く。`{string}` は引用符の値、`{n}` は数(Examples の値に合わせて `{int}` か `{float}`)、`<p>` は Examples の列。共通の文言は 33a の `common.rs` にあるので書かない。

### 課題の見つけ方

- 判断モデルが迷いの度合いを <p> で答え、確信度 {n} で {string} を選ぶ
- そのステップは判断に迷う手がかりとして<p>
- 判断モデルが迷いの度合いを {n} で答え、確信度 <p> で {string} を選ぶ
- 前のステップで画面 {string} から画面 {string} へ移った
- 判断モデルが back を返し、ガードレールを通って実行される
- そのステップは判断に迷う手がかりとして記録されている
- 試行の中で画面 {string} と画面 {string} の間を移っている
- 操作の結果、{string}、{string}、{string}、{string} の順に画面が移る
- 2つの画面の行き来が、判断に迷う手がかりとして記録されている
- 行き詰まりの回数は、行き来を記録したことでは増えていない
- 行き詰まりの閾値は {n} 回に設定されている
- 操作のたびに未操作の要素を操作していて、行き詰まりの回数は {n} である
- 同じ2つの画面の間を {n} 回行き来する
- 試行は終わっておらず、次のステップで判断モデルに問い合わせる
- 判断モデルが、スクリーンショットを見て、ボタン {string} を目立たない要素として挙げる
- 台帳に、{string} を対象とした視認性が悪い課題が出ている
- どのステップでも、判断モデルが見えにくい要素を挙げない
- 台帳に、視認性が悪い課題は出ていない
- 試行が画面 {string} で行き詰まりとして終わる
- 判断モデルが、最後のステップの期待を {string} と答えている
- 台帳に、画面 {string} の目的に届かない課題が出ている
- その課題の理由に {string} が書かれている
- 橋渡しが起動のときに、画像を扱えないと申告する
- 台帳に、視認性を確かめなかったことが書かれている
- 判断に迷う課題が起きるステップで、画面のスクリーンショットを撮っている
- 橋渡しに書いた問いの JSON に、画像は含まれていない
- 台帳のその課題には、撮ったスクリーンショットの場所が書かれている
- 判断モデルの応答に、見えにくい要素の答えが無い
- 応答の異常として記録されていない
- 判断モデルが選んだ操作を、ガードレールを通したあとに実行している
- 橋渡しが起動のときに、画像を扱えると申告する

### 台帳の書式

- 試行の中で課題が2件見つかっている
- 台帳は Markdown の1つのファイルである
- 各課題の1行目は、直す指示の文である
- 試行の中で、判断に迷う課題が1件見つかっている
- その課題は次の項目を持つ
- 各課題に、画面の要素の手がかりが書かれている
- 各課題に、ソースファイルの名前や行番号の項目は無い
- 判断に迷う課題が、3回の試行のうち1回だけで起きている
- その課題は台帳の本体にあり、3回のうち1回起きたと書かれている
- 3回のうち1回起きた課題 A と、3回のうち3回起きた課題 B と、3回のうち2回起きた課題 C がある
- 台帳の本体の課題は B、C、A の順に並んでいる
- 課題の番号が {string} と {string} の課題が、どちらも3回のうち2回起きている
- {string} の課題が {string} の課題より前にある
- 前回の実行で、画面 {string} のボタン {string} に判断に迷う課題が出ている
- 同じ設定でもう一度実行し、同じ画面の同じ要素に判断に迷う課題が出る
- 今回の課題の番号は前回と同じである
- 画面 {string} のボタン {string} に、判断に迷う課題がある
- <p> の課題が出る
- 2つの課題の番号は違う
- 前回の実行で、画面 {string} に目的に届かない課題が出ている
- 同じ設定でもう一度実行し、同じ画面で目的に届かない課題が出る
- 画面 {string} の目的のずれの課題が出れば、その番号は目的に届かない課題と違う
- 番号 {string} の課題が、2回目の試行のステップ {n} で起きている
- 判断モデルが、その課題の理由に {string} という文を書いている
- その課題のスクリーンショットの名前は、{string}、{n}、{n} だけから作られている
- その名前に {string}、{string}、{string} は含まれない
- 課題が3件あり、そのうち1件を選んだ台帳がある
- 3件の課題の番号、種類、項目の中身が書いたときと同じに戻る
- 選んだ課題は1件だけである
- 判断モデルが、期待の文として <p> を返す
- 台帳を書き、それを読み戻す
- 読み戻した台帳の課題の数と選択は、書いたときと同じである
- その文は1つの課題の期待として、元の文字列のまま読み戻せる
- 直す指示の文の元になる判断モデルの文に改行が入っている
- 課題の1行目の直す指示の文に改行は無く、2行目以降に指示の続きは書かれていない
- 判断モデルが、理由の文に {string} と書く
- 台帳には {string} が無く、伏せる対象の名前が書かれている
- 台帳に、ペルソナの名前 {string}、開始の URL {string}、終えた試行の回数 {n} 回が書かれている
- 目的は、推測の印と推測した文で書かれている
- 試行の中で判断に迷う課題が見つかり、確定の問題は記録されていない

`{string}`、`{int}`、`{float}` 以外の広いパラメータと正規表現は使わない。Examples の値で手順を分ける必要があるときは、値から場面への対応表で引く。手順の中に `if` を書かない。

## 場面の組み立てと使う製品の口

- 課題は `webqa_core::interview::ledger::read` で読み戻した値で確かめる。課題の番号は `I-` と16進8桁で、feature の例の番号は 33a の補助で実際の番号に読み替える。
- 台帳の課題の1行目は `- [ ] I-XXXXXXXX 指示の文`。「1行目は直す指示の文」の確かめは、番号より後を指示の文として読む。
- 台帳の書式の Rule は、書き出した本文そのもの(節の順、空の節の書き方、伏せ字)を確かめるシナリオがある。本文の比べ方は、行を取り出して値ごと比べる。

## 注意

- 壊れたときに止まり続けるテストを書かない。`tokio::time` はこのクレートで禁止なので、待つなら std の `recv_timeout` か `tests/support/stuck.rs` を使う。
- シナリオを通すために Then の確かめを緩めない。Given の場面を feature と違うものにしない。親のまとめてのレビューは、何も確かめずに通るシナリオを must として探す。
- 期待値は値ごと比べる。Debug の文字列や部分一致で済ませない。
