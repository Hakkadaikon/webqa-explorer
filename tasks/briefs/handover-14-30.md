# #14 と #30 への申し送り

ほかの issue の brief とレビューで見つかり、#14(実行ループと CLI)か #30(試行の外のループ)で受け持つと決めたことを、brief を書くまでここに溜める。

## #14(実行ループと CLI)

- issue #14 のコメントにある引き継ぎ4件(.env の読み込み、イベントログの書き出しの伏せ字、URL の伏せ字ほか)。
- 決め打ちシナリオのモードで、設定に `scenario` が無ければ設定エラーにする。今は `config::mode` が確かめず、段階が空だと中核はゴールに達しない(12d の brief)。
- 12e が入ったら、`run.rs` の `observe` で、観測のページ全体の要素と文字列(`Observation` の `outline` と `text`)から `Whole` を作る。入るまでは `Whole::plain` で、見出しを指す done_when(T-092)は成り立たない。
- `run.rs` の `observe` は、まだ `Material::plain` で材料を作っている。9b の `Observation` の `nodes`、`candidates`、`paywall` から `Material` を作り、禁止要素・要素の参照・課金画面の判定に本物の材料を渡す(12b と 9b を統合した時点の残り)。
- 受け入れのテストで T-084 に使うページには要素を置く(3段目の絞り込みで操作が3つだけになるため)。
- 確率の欠けと0を記録で区別する必要が出たら、`Touch.confidence` を `Option<f64>` に変える(12b は欠けを 0.0 にしている)。
- イベントログの `run_finished.reason` には終了理由の serde の名前を書く。行き詰まりの種類(判断モデルの宣言か、回数か)を別の項目で残すか、終了コードを `is_stuck` で決めるかを決める(12b の brief)。
- 判断モデルの「判断」と、中核が自分で出す操作(reload、return、課金画面の離脱)を、イベントログで別の種類にする(#15 のレビュー)。
- 問題の検出(#8 の関数)の呼び出しと、イベントログ・実行結果への書き出し。
- 課金画面の既定の離脱操作に、ブラウザの操作の表に無い名前を設定できないよう、設定の検証で縛るかを決める(12b の brief)。
- tracing の購読側で、依存の `playwright_rs` の水準を `info` 以下に固定する。playwright-rs 0.20.1 は `trace` の水準で要求の JSON を出し、そこに `fill` の値(秘密の値)が入る(9b のレビュー)。
- `input` の対象は入力欄の系統に絞る。チェックボックスやボタンへの `fill` は Playwright がすぐ失敗を返し、`BrowserError` で実行が止まる(9b のレビュー。12d と合わせて決める)。
- 判断モデルの橋渡しのコマンドが自分の時計を持つので、偽の時計で待ち時間切れの受け入れを書くときは、実行ループの時計と揃える(#15 のレビュー)。

## #30(試行の外のループ)

- 中断で `run` の future を途中で捨てたあと、初期化のコマンドの子プロセスが残らないことを確かめるテスト(`kill_on_drop` の保証。#28 のレビュー)。
- 初期化のコマンドが標準出力か標準エラーを開いたままの裏の処理を残すと、読み取りが終わらず待ち時間切れになる。利用者向けの説明に書く(#28 の brief)。
- 初期化のコマンドの待ち時間切れが、実行全体の期限を越えたときに、初期化の失敗として扱うか時間切れの打ち切りとして扱うかを決める(#28 の brief)。
- #12 の終了理由を #21 の `Ended` に写す。行き詰まりは、判断モデルの宣言を `Stuck::GaveUp`、回数を `Stuck::NoProgress` にする。
- `limits.max_duration_secs` を `Option<Duration>` にし、実行全体の窓を `RequestWindow::new(interview.requests_per_hour)` で作る(#26 の brief)。
- 初期化のコマンドの子に渡す環境変数から、API キーの値を除く(`std::env::vars_os()` と `[api_key.expose()]` を渡す。#28)。
- #18 の `Reset` の `Debug` は引数を出す。ログに `{:?}` で書かない。直すかは別に決める。
- 中核の状態機械が、インタビューのモードでは `interview::ask` と `interview::answer`(#20)で問いを組み立て、答えを読むようにつなぐ。12d の候補の絞り込みとの関係もここで決める(#20 の brief)。
- スクリーンショットをどこから得るかを決める(`ports::Observation` に入れるか、別の効果にするか)。#20 は `shot: Option<&Image>` で受ける(#20、9b の brief)。
- 判断モデルが自由な文の答え(期待、目的の推測、見えにくい理由)に秘密の値を書き写すことがある。台帳やログに出す前に伏せ字を通す(#20 の brief。#24 とも関わる)。
- ずれの問いを送るときに `Judge::ask` へ渡す画面の文字列を決める。案は、その URL の型に最初に合った観測の画面(#20 の brief)。

## #33(インタビューのモードの受け入れ)

- 課題の番号は `I-` と16進8桁で、画面・要素・種類から計算する(#22 の brief)。仕様の例の番号(`I-0001` など)は、受け入れの手順の中で実際の番号に読み替える。
- 台帳の課題の1行目は `- [ ] I-XXXXXXXX 指示の文`。「1行目は直す指示の文」の確かめは、番号より後を指示の文として読む(#24 の brief)。
