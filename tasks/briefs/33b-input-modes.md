## 受け持つシナリオ

### ペルソナと目的の入力(19本)

- 形式の正しいペルソナの文書を読み込んで実行を始める
- ペルソナの文書に必須の項目が欠けていたら設定エラーにする
- ペルソナの文書が決まった形式で読めなければ設定エラーにする
- 目的を書いたときは、目的の done_when を満たしたかで達成を判定する
- 目的を書かなかったときは、判断モデルが推測した目的を台帳に書く
- 画面ごとの目的の項目で、推測が書いた目的と同じでないと判断モデルが答えたら、目的のずれの課題を出す
- 目的のずれの課題は、URL の型を画面とし、出現回数と届いた試行の数をその型に届いた終えた試行の数で書く
- 同じ URL の型に合う複数の画面の推測を、重複をまとめて1回だけ聞く
- 推測の文字列が書いた目的と違っても、同じことを指すと判断モデルが答えたら、目的のずれの課題は出さない
- 画面ごとの目的の URL の型に合う画面に届いた試行が無ければ、ずれの問いを聞かない
- その URL の型に合う画面に届いたのが打ち切りの試行だけなら、ずれの問いを聞かない
- その URL の型に合う画面に使える推測が1つも無ければ、ずれの問いを聞かない
- ずれの問いの答えが使えなければ、ずれの課題を出さず確かめられなかった区分に入れる
- ずれの問いは自然さの問いと同じ上限に数え、超えた分は確かめられなかった区分に入れる
- 目的のずれの課題も、自然さの問いにかける
- 画面ごとの目的を書いていない画面では、推測した目的をずれとして比べない
- 画面ごとの目的の URL の型が書式に合わなければ設定エラーにする
- 試行の回数や閾値が範囲の外なら設定エラーにする
- 行き詰まりの閾値は、インタビューのモードだけ別の値にできる

### 既存のモードとの関係(5本)

- 探索モードと決め打ちシナリオの受け入れシナリオは、そのまま通る
- インタビューのモードでも、既存のガードレールで止まる操作は実行しない
- インタビューのモードでも、判断モデルの呼び出しが上限に達したら試行を止める
- インタビューのモードでも、設定で指定した機密情報は判断モデルに送るテキストで伏せる
- インタビューのモードは課題を直さず、台帳と実行結果のほかにファイルを書き換えない

名前は、Rule のファイルの `READY` に入れる。

この Rule にだけ出る文言を書く。`{string}` は引用符の値、`{n}` は数(Examples の値に合わせて `{int}` か `{float}`)、`<p>` は Examples の列。共通の文言は 33a の `common.rs` にあるので書かない。

- 1回目の試行が始まっている
- ペルソナの文書に <p> が書かれていない
- インタビューのモードで実行しようとする

- 判断モデルは done を返さない

- ずれの問いは、その URL の型について1回だけ聞かれている
- 画面ごとの目的として、URL の型 {string} に {string} を書き、試行の回数は {n} 回である

- 目的のずれの課題の画面は URL の型 {string} で、対象の要素は無い
- その課題は、2回の試行のうち2回起きたと書かれ、その画面に届いた試行の数は {n} である
- その課題のスクリーンショットは1回目の試行のステップ {n} のもので、名前は課題の番号、{n}、{n} から作られている
- 判断モデルが、URL {string} の画面の目的を {string}、URL {string} の画面の目的を {string} と {string} と推測する

- その問いに渡した推測は {string} と {string} の2つである
- 判断モデルが、URL {string} の画面の目的を {string} と推測する
- すべての試行を終えたあとのずれの問いで、判断モデルが、これらの推測は書いた目的と同じことを指すと答える

- 判断モデルに、その URL の型のずれの問いは聞かれていない

- 試行は行き詰まりで終わっていない
- {n} 回目でその試行は行き詰まりとして終わる

### 既存のモードとの関係

- インタビューのモードを足した版である
- 探索モードと決め打ちシナリオの受け入れシナリオをすべて回す
- すべてのシナリオが通る
- <p>
- ブラウザで <p> を操作していない
- 1回の試行で判断モデルを {n} 回呼び出す
- その試行は判断予算切れとして終わっている
- 判断モデルに渡したアクセシビリティ情報のテキストに {string} は無い
- 書いたファイルは、台帳、イベントログ、実行結果、スクリーンショットだけである
- 対象の Web アプリに、課題を直すための操作をしていない

`{string}`、`{int}`、`{float}` 以外の広いパラメータと正規表現は使わない。Examples の値で手順を分ける必要があるときは、値から場面への対応表で引く。手順の中に `if` を書かない。

## 場面の組み立てと使う製品の口

- 設定とペルソナと目的の文書の誤りは、ブラウザを開く前に設定エラー(終了コード2)になる。`webqa::setup::load_interview` と `webqa_core::config::interview::load` を呼び、起動の偽物が一度も呼ばれないことを確かめる。
- 目的を書かない設定(推測させる)と、書いた設定の両方を場面で作る。共通の手順「目的を設定に書いていない」を使う。
- 既存のモードとの関係の5本は、インタビューのモードの設定が既存の探索モードと決め打ちシナリオのモードの振る舞いを変えないことを確かめる。既存のモードの実行は、探索モードの受け入れの場面を作り直さず、`webqa::run::session::conduct` を偽物の部品で1回回す形にする。インタビューのモードでない実行が判断モデルにテキストだけを送ることは、問いの記録の画像の有無で確かめる。

## 注意

- 壊れたときに止まり続けるテストを書かない。`tokio::time` はこのクレートで禁止なので、待つなら std の `recv_timeout` か `tests/support/stuck.rs` を使う。
- シナリオを通すために Then の確かめを緩めない。Given の場面を feature と違うものにしない。親のまとめてのレビューは、何も確かめずに通るシナリオを must として探す。
- 期待値は値ごと比べる。Debug の文字列や部分一致で済ませない。
