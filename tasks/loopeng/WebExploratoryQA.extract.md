# 抽出台帳: WebExploratoryQA

元仕様
  - (A) 参考記事「Jevを使ってiOSアプリの動作確認を自動化する」(jev-qa: AXe + Jev + Python + YAMLによるiOSアプリ探索的テストツール)
  - (B) ユーザーの口頭要求「このjevのQAシステムをさらに実用化したOSSを開発したい」「webサービスの探索的テストシステムとしてつくってほしい」

走査アンカー: 記事(A)の各節(見出し単位) + ユーザー要求(B)の機能語(「実用化」「OSS」「Webサービス」)を単位に、Web版への翻案前提で要件候補を列挙する。規範語なし散文のため、各文/各仕組みを候補として分類する。

注記: 「原文抜粋」欄の多くは、記事中の箇条書き・表のセル(見出し語+短い説明)を1行に合成した要約であり、逐語引用ではない。原文の正確な文言は出典の§番号から記事を直接参照して確認すること。

各IDは元仕様の最小単位1つ。EARSへ変換し終えたら`[x]`。
`[ ]`が1つでも残る、連番に欠番がある、または下の「閉じる前のチェック」に未記入があるうちは外ループ(EARS/TLA+)へ進めない。
1 IDが複数EARSに割れてよい(正常系+そのunwantedなど。過剰抽出は安全)。

各行のEARS本体は原則1〜2行に収める。ただし1 IDが複数の状態/正常系+unwanted等に割れる場合(13行目)、分割後の各EARS文が短い1文であれば3行以上になってもよい(S-021等)。出典・他IDとの関係・レビュー対応の経緯などの補足は、行に埋め込まず**末尾の「設計メモ」節**にID別に集約する(2026-10-17、EARS行の肥大化を指摘されたため台帳を再構成)。

## 台帳

      → WHEN 判断モデルが操作種別と対象要素を返しガードレールで禁止されていないとき、システムはその操作種別・対象要素に従ってブラウザ操作を実行しなければならない。(event)

- [x] S-004 (A)§3 「YAML設定ファイル：アプリ固有のルールとシナリオを定義」
      → システムはテスト対象・入力値・段階をYAML設定で定義できなければならない。(ubiquitous)

      → WHEN 1ステップを実行するとき、システムは現在画面にエラー表示があるかを判断モデルに問い合わせなければならない。(event)
- [x] S-008 (A)§4 「goal_achieved(noul): ゴール達成の有無」
      → WHEN 1ステップを実行するとき、システムは現在のゴール達成有無を判断モデルに問い合わせなければならない。(event)
- [x] S-009 (A)§4 「要素一覧はstateにも含める必要があった」
      → システムは判断モデルへ送るstateに操作可能要素一覧を含めなければならない。(ubiquitous)
- [x] S-010 (A)§5 「自信度0.7未満の『戻る』は実行しない」
      → IF 判断モデルが返した操作がbackかつ確信度が0.7未満のとき、システムはその操作を実行してはならない。(unwanted)
- [x] S-011 (A)§5 「画面が変わらないのに同じ要素を押そうとした場合、次に確率が高い要素に切り替える」
      → IF 直前の操作後に画面が変化せず同じ要素を再度選択しようとしたとき、システムは次に確信度の高い候補要素へ切り替えなければならない。(unwanted)
- [x] S-012 (A)§5 「購入・削除・退会・サインインのボタンは押さない」
      → IF 対象要素が購入・削除・退会・サインイン等の破壊的/決済操作に分類されるとき、システムはその要素を操作してはならない。(unwanted)
- [x] S-013 (A)§5 「課金画面が出たら、Jevに判断させず左上の×を押す」
      → IF paywall相当のUIが検出されたとき、システムは判断モデルに問い合わせず既定の離脱操作を実行しなければならない。(unwanted)
- [x] S-014 (A)§5 「自己申告は信用せず、done_whenをツール側で確認する」
      → システムはゴール達成を判断モデルの自己申告ではなく、各stageのdone_when条件で判定しなければならない。(ubiquitous)
- [x] S-015 (A)§5 「長いゴールは段階に分けた」
      → システムは1つのシナリオを複数のstageに分割して定義できなければならない。(optional)
- [x] S-016 (A)§6 「--explore 秒数で、未押下のボタンを優先して触り続ける」
      → システムは指定時間だけゴールなしで未操作要素を優先的に操作し続ける探索モードを提供しなければならない。(optional)
- [x] S-017 (A)§6 「固まる、アプリ外に出る、行き詰まる場合はアプリを再起動して続行する」[設計メモ2]
      → IF 探索中にページが応答しない・対象ドメイン外に遷移した・行き詰まり状態になったとき、システムは対象ページを初期状態に戻して探索を継続しなければならない。初期状態に戻すのはページの状態だけで、探索の記憶(S-022)は保持する。(unwanted)
- [x] S-018 (A)§6 「気になる点はISSUE_<種類>_step<番号>.pngの名前でスクリーンショットを保存する」
      → WHEN 問題が検出されたとき、システムは種類とステップ番号を含む命名でスクリーンショットを保存しなければならない。(event)
- [x] S-019 (A)§6 「エラー表示: Jevが判定」
      → IF is_error_shownの確信度が設定閾値以上のとき、システムはエラー検出として記録しなければならない。(unwanted)
- [x] S-020 (A)§6 「読み上げ名が画像ファイル名、仮の値: スクリプトが判定」
      → IF 操作可能要素のアクセシブルネームが画像ファイル名形式または既定のプレースホルダ値に一致するとき、システムはアクセシビリティ上の問題として記録しなければならない。(unwanted)
- [x] S-021 (A)§6 「固まり、アプリ外、行き詰まり: ツールが判定」[設計メモ3]
      → システムは一定時間操作後も画面に変化がない状態を「固まり」として判定しなければならない。(state)
      → システムは操作の結果が許可ドメインの外への遷移であることを検出できなければならない。(state)
      → システムは既定の試行回数操作しても新規要素が出ない状態を「行き詰まり」として判定しなければならない。新規要素が出ないとは、操作の結果、探索済みの要素の集合が増えないことをいう。(state)
- [x] S-022 (A)§6 「探索の記憶: 画面と遷移をグラフとして実行をまたいで保存」
      → システムは画面状態と操作による遷移を実行をまたいで永続化したグラフとして保持しなければならない。(ubiquitous)
- [x] S-023 (A)§6 「未押下優先→未探索分岐残り優先→戻る/スクロールの順で選択」
      → システムは未操作要素→未探索分岐が残る既操作要素→戻る/スクロールの順で次の操作を選択しなければならない。(ubiquitous)
- [x] S-024 (A)§6 「途中のボタンは先が探索済みになるまで『済み』にしない」
      → システムは操作した要素について、遷移先がすべて探索済みになるまで当該要素を探索済みとして扱ってはならない。(unwanted)
- [x] S-025 (A)§7 「速度評価: 判断は全体の一部、操作・画面変化待ちがボトルネック」
      → システムは判断・操作・画面変化待ちにかかった時間を計測・記録できなければならない。(optional)
- [x] S-026 (A)§7 「料金評価: 1ステップ/シナリオ/探索あたりのコストを算出」
      → システムは判断モデル呼び出しのトークン数・回数からコストを算出・記録できなければならない。(optional)
- [x] S-027 (A)§8 「使い分けの方針」
      → システムは決め打ちシナリオ実行モードと探索モードの両方を同一ツールで提供しなければならない。(ubiquitous)
- [x] S-028 (A)§10 「失敗談(課金画面)。対策は直前の要素存在確認・課金入口を押さない」
      → IF 実際に操作を実行する直前に対象要素が存在しないとき、システムは操作を中止しなければならない。(unwanted)
      → IF 対象要素が決済導線に分類されるとき、探索モードはその要素を選択してはならない。(unwanted)
- [x] S-029 (A)§10 「『わかりにくい表示』の判定はJevでは誤検知が多く実用性は低かった」
      → システムは意味判断を要する検出項目について、判断モデル単独の判定結果を低信頼度の参考情報として扱い、確定的な不具合判定とは区別して記録しなければならない。(ubiquitous)
- [x] S-030 (B) 「Webサービス向けの探索的テストシステムとして作ってほしい」
      → システムはWebブラウザを操作対象として探索的テストを実行できなければならない。(ubiquitous)

- [x] S-032 (推測) 「Webならではの認証・ログイン状態の扱い」
      → システムは探索開始前に指定された認証状態を注入できなければならない。(optional)
- [x] S-033 (推測) 「Webならではのナビゲーション境界(外部ドメイン遷移)」
      → IF 操作の結果、対象ページが許可ドメインの範囲外に遷移したとき、システムはその遷移を記録し探索対象外として扱わなければならない。(unwanted)
- [x] S-034 (A)§9 「再現手順をすぐに確認でき、原因の調査につなげられた」[設計メモ4]
      → システムは実行結果(発見した問題・操作ログ)を再実行可能な形式で出力しなければならない。(optional)
- [x] S-035 (A)§6 「問題の記録の種類の分類」まとめ
      → システムは検出した問題を種類別に分類して記録しなければならない。(ubiquitous)
- [x] S-036 (推測) 「JavaScriptエラー・コンソールエラーの検出」
      → IF 探索中にブラウザのコンソールにエラーログが出力されたとき、システムはそれを問題として記録できなければならない。(optional)
- [x] S-037 (推測/セキュリティ境界) 「判断モデルAPIへ送信する画面情報に機密情報が含まれる可能性」
      → システムは判断モデルへ送信するアクセシビリティ情報から、設定で指定された機密情報をマスキングできなければならない。(unwanted/security)
- [x] S-038 (推測) 「設定ファイルの秘密情報(APIキー等)の扱い」
      → システムは判断モデルAPIキー等の秘密情報を環境変数等の外部参照で設定できなければならない。(unwanted/security)
- [x] S-039 (調査結果)[設計メモ5] 「判断モデルの差し替え可能性」
      → システムはnoul/choice/scoreの3型質問インタフェースを抽象化し、Jev以外の判断モデルへ差し替え可能でなければならない。(ubiquitous)
- [x] S-040 (調査結果) 「アクセシビリティ情報取得APIの実装選択」
      → システムは非推奨APIに依存せず、現行のPlaywright `ariaSnapshot()`相当のAPIでアクセシビリティ情報を取得しなければならない。(ubiquitous)
- [x] S-041 (STRIDE: D観点) 「判断モデルAPI呼び出しの無制限実行によるコスト膨張の防止」
      → システムは判断モデルAPIへの呼び出し回数または実行時間に上限を設定でき、上限に達したとき実行を停止しなければならない。(unwanted/security)
- [x] S-042 (STRIDE: D観点) 「探索モードによるテスト対象サーバへの過度な負荷の防止」
      → システムは探索モードにおける単位時間あたりの操作回数に上限を設け、対象サーバへの過度な負荷を避けなければならない。単位時間の窓は時刻で区切られ、どの時点でも満了しうる。(unwanted/security)
- [x] S-043 (STRIDE: S観点)[設計メモ6] 「判断モデルAPIとの通信でTLS証明書検証を無効化してはならない」
      → システムは判断モデルAPIへの通信でTLS証明書検証を無効化する設定を使用してはならない。(unwanted/security)
- [x] S-044 (補足要件)[設計メモ7] 「判断結果がdoneまたはstuckのときの実行終了の扱い」
      → WHEN done_when条件が満たされたとき、システムは実行をゴール達成として記録しなければならない。(event)
      → WHEN operation=doneが返されたがdone_when条件が満たされていないとき、システムは実行を未検証の終了(reported_done)として記録しなければならない。(event)
      → WHEN operation=stuckが返されたとき、またはS-021の行き詰まり検出条件が成立したとき、システムは実行を行き詰まり終了として記録しなければならない。(event)
      → WHILE 判断を問い合わせる前の待機状態にあるとき、システムはゴール達成(S-014)、行き詰まり(S-021)、判断予算切れ(S-041)、固まり復旧・ドメイン復帰・リクエスト窓の満了(S-017, S-033, S-042)、判断の問い合わせの順に、成り立つ条件のうち最も優先度の高いものだけを実行しなければならない。(state)

## 設計メモ(ID別の補足・他IDとの関係・レビュー対応の経緯)

1. **S-005**: 原文のoperationの選択肢は「タップ／入力／下スクロール／上スクロール／戻る／待つ／完了／行き詰まり」の8種。上下スクロールを1つの`scroll`に統合すると情報量を減らした変換になるため、8種のまま維持する。
2. **S-017**: 固まる/アプリ外/行き詰まりの3条件はOR→単一アクション(「初期状態へ戻して続行」)として0段で1文のまま抽出した。ただしformalize工程のTLA+実装では3条件それぞれ異なる扱いになった(固まりのみ`RecoverFromFreeze`で復旧、ドメイン外は`ExecuteOutOfDomain`/`ReturnToAllowedDomain`で継続、行き詰まりは`FinishStuck`で終了)。「結果のアクションが1つに収束する」という0段時点の想定はformalize実装と一致しなかったため、トレーサビリティ・マトリクスのS-017行に実装の実態を注記した。詳細は`WebExploratoryQA.faithfulness.md`のS-017説明を参照。
   - S-018も同様に6条件のOR→単一アクション(命名規則に沿ったスクリーンショット保存)として1文のまま抽出し、こちらは実装も単一アクションのまま変わっていない。
   - S-021は同じ3条件を「異なるstate名への判定」としてS-017とは別に3文へ分割した。S-017(復旧アクション)とS-021(検出条件)は検出→復旧の前後関係にあるが、一方が他方に吸収されるものではない独立要件。
3. **S-019 / S-021**: S-007(is_error_shownの値取得)・S-017(固まり検出後の復旧アクション)とは別の独立した新規要件。S-019はS-007で取得した値を閾値判定して検出イベントに変換する要件、S-021はその検出条件自体を定義する要件であり、いずれも吸収・統合ではない。
4. **S-034**: 出典は(A)§9「見つけたときにはスクリーンショットと操作の記録が残っているので、再現手順をすぐに確認でき、そのまま原因の調査につなげられました」。この一文を当初は「結果報告でテスト要件を含まない」として対象外にしていたが、再現性要件の直接の一次出典であると判明したため§9由来に修正した(記事を再取得し原文と逐語一致を確認済み)。

6. **S-043**: 2回目のformalizeレビューでSTRIDE(S観点, 判断モデルAPI境界)の「該当なし」判断が手薄と指摘され追加。当初「TLS証明書検証失敗時にクライアントが接続を続行してしまう」という理由で要件化したが、3回目レビューで「ライブラリの既定動作をアプリ側で再実装するよう要求する過剰設計」と指摘され、「TLS証明書検証を無効化する設定を使用してはならない」という禁止系の文言に修正した。既定のHTTPSクライアントはTLS検証失敗時に例外を投げて続行しない動作を持つため、独自の検証・停止ロジックの実装は要求せず、検証を無効化しないことだけを要件化する。
