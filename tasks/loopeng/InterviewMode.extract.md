## 状態機械とTLA+の検査について(この台帳での判断)

このモードではTLA+のspecを書かず、TLCも回さない。ユーザーの判断で、追加のTLA+の検査は要らないとした。
理由は、このモードが中核の状態機械の遷移を変えないためである(設計L64-67、L290-291)。
1回の試行は中核の1回の実行で、既存のspec(`WebExploratoryQA.tla`)の`mode = scenario`の道筋をそのまま通る。
変わるのは、状態機械の外側にある問いの中身、候補の選び方、課題の検出、出力、試行の繰り返し(下の「状態機械の外の新しいループ」)と、中核へ渡す入力の値である。
中核へ渡す入力で変わるのは次の3つで、どれも既存のspecでは定数か環境の事象にあたる。この3つは【ユーザー承認済み】(記録7)。
- 時刻の起点: 実行の開始からの経過時間を渡す(S-097)。specでは時刻は環境の事象`TimeElapses`と`ResetRequestWindow`の起きる時点にしか現れない。
- 時間窓の上限の値: 試行ごとに定数`MaxRequests`の値を変えて渡す(1以上。S-097)。
- 制限時間の期限: 実行全体で1つの期限を各試行に渡す(S-094)。specでは`TimeElapses`が起きる時点が変わるだけである。
既存のTLCの結果は、`WebExploratoryQA.cfg`と`WebExploratoryQA.noexplorable.cfg`に書いた小さな定数の値での結果である。定数の値を試行ごとに変えても遷移の形は同じだが、TLCがそのすべての値を検査したわけではない。値の大きさに依る性質は、既存の全状態の探索のテスト(`docs/architecture.md`の「決定的なテスト」)と、下のループの性質テストで確かめる。
抽出の途中で、遷移を変える要件は見つからなかった。遷移に近かった点と、遷移を変えずに済ませた解釈は設計メモ1に書いた。
そのため、トレーサビリティ・マトリクスの「形式手法」列は、既存のspecの遷移を使うか、状態機械の外かのどちらかで埋める。状態機械の外の新しいループの行は、検証の方法を「性質テスト」と書く。

## 状態/ドメインモデル

状態機械(既存のspec)の変数は増やさない。このモードで足す名詞は、状態機械の外側のドメインの値である。

| 名詞 | 型(値域) | 初期 | 不変条件・備考 |
|---|---|---|---|
| ペルソナ `Persona` | 名前、どんな人か、ITの慣れ、達成したいこと、知らないこと・しないこと(5つとも空でない文) | 文書から読み込んで検証 | 5項目が欠ければ設定エラー(S-016, S-017) |
| 目的 `Purpose` | 実行の目的1つ(`Written { done_when }` か `Inferred`)と、任意の画面ごとの目的の列(URLの型, 目的の文) | 設定から決まる | `Written`のdone_whenは宣言を1つ以上持つ(設計メモ1-c)。URLの型が不正なら設定エラー(S-103) |
| 試行の回数 `trials` | 1以上100以下の整数 | 設定(既定値あり) | 範囲の外は設定エラー(S-083) |
| 試行 `Trial` | 中核の1回の実行の結果(終了理由、届いた画面の集合、ステップごとの答え) | 試行ごとに中核の`Init`から | 試行どうしは中核の状態を共有しない(S-027, S-029, S-094)。制限時間の期限だけは実行全体で1つ |
| 試行の結末 | {終えた, 打ち切り} | なし | 打ち切りは、利用者による中断か、実行全体の期限(中核の時間切れ)で終わった試行。終えた試行の数をNとし、打ち切りはNにも目的に届かない試行にも数えない(S-049, S-093) |
| 実行全体の時間窓 `RunWindow` | 窓の番号(実行の開始からの経過時間÷1時間)、その窓のアクセスの数u(0以上、上限以下) | 番号0、数0 | 試行をまたいで数える。中核の時間窓とは区切りの時刻が同じで、数は別。試行の最初のページの表示も1回に数える。初期化のコマンドのアクセスは数えない(S-101)。次の試行に渡す中核の上限は「上限−u−1」で、それが上限の半分を下回れば窓が明けるまで待つ(S-097) |
| 画像の申告 | 真偽(橋渡しが起動時に、JSONの版の項目で申告) | 起動時に読む | 偽なら見えにくい要素の答えを求めず、視認性の課題を出さない(S-031) |
| 迷いの手がかり | 迷いの度合い≧閾値、確信度<閾値、引き返し、同じ画面の行き来 | なし | 行き詰まりのカウンタには入れない(S-048) |
| 課題 `Issue` | 番号、種類{迷い, 視認性, 目的に届かない, 目的のずれ}、画面、要素(無いこともある)、指示の文、出現回数k/N、その画面に届いた試行の数、ペルソナの性質ほか(S-058) | 試行の結果から作る | 番号は、要素を持つ課題は(画面の識別, 要素の識別, 種類)、目的に届かない課題は(画面の識別, 種類)、目的のずれの課題は(画面ごとの目的のURLの型, 種類)の決定的な関数(S-059)。目的のずれの課題は、画面=URLの型、要素=無し、N=その型に合う画面に届いた終えた試行の数、k=N、その画面に届いた試行の数=N、スクリーンショット=その型に最初に合った観測のもの(S-021, S-058, S-104)【親】。0≦k≦N |

| 目的のずれの判定(用語「目的のずれ」の定義) | 画面ごとの目的の1項目(URLの型1つ)ごとに{ずれ, 同じ, 確かめられなかった, 聞かない} | すべての試行を終えたあとに決める | 文字列の一致では決めない。項目1つにつき1回、その型に合う画面で終えた試行の中に出た推測を全部(前後の空白を除いた文字列で重複をまとめたもの)と書いた目的を判断モデルに渡し、「これらの推測は書いた目的と同じことを指すか」を聞く。同じでないと答えたら「ずれ」で、その項目の目的のずれの課題になる。型に合う画面に届いた終えた試行が無いか、使える推測が1つも無ければ聞かない。答えが使えないか上限を超えれば確かめられなかった。回数は自然さの問いと同じ上限に数え、ずれの問いを先に聞く。判断予算には数えない(S-021, S-102)【親】 |
| 照らし合わせ | {新しく出た, 残っている, 解消した, 確かめられなかった} | 前回の台帳が無ければ全件「新しく出た」 | 「解消した」は、今回その画面に届いた試行の数≧前回その画面に届いた試行の数、かつk今回=0のときだけ。足りなければ「確かめられなかった」(S-070, S-071) |
| 選択 | 真偽(チェックボックス) | 新しく出た課題は偽 | 残っている課題は前回の値を引き継ぐ(S-072) |
| 台帳 `Ledger` | Markdownの1ファイル。ペルソナ名、目的(推測の印を含む)、開始のURL、N、課題の列(本体)、確かめられなかった課題の節、外れた課題の節(最後) | 実行の終わりに書く | 書いて読み戻すと同じ値に戻る(S-057)。並びは割合の降順、同率は番号の昇順(S-061) |

既存のspecとの対応は次のとおり。

| このモードの事象 | 既存のspecでの扱い |
|---|---|
| 目的を書いた試行 | `mode = scenario`、段階は1つ。done_whenの成立で`FinishNormally` |
| 目的を書かない試行 | `mode = scenario`で、done_whenが成り立たない段階1つ。doneは`FinishByProposalDone`(未検証の終了) |
| stuck(ペルソナが諦めた) | `FinishByProposalStuck` |
| 行き詰まり、判断予算切れ、時間切れ、中断 | `FinishStuck`、`ExceedDecisionBudget`、`FinishTimeUp`、`UserAbort` |
| 候補を絞らない選び方 | `RequestDecision`の中身(優先順位の中身は既存でもモデル外) |
| 追加の問い(迷い、期待、見えにくい要素、目的の推測) | 1つの`RequestDecision`の中で判断モデルを2回呼ぶ(期待は2回目)。2回目の失敗は既存の応答の異常の道筋。`decisionBudget`と`decisionsMade`は判断のステップ数で、API の呼び出し数ではない |
| 自然さの問い、指示の文、台帳の書き出し | 試行の後に実行ループの外で行う。状態機械に入らない |
| 試行の繰り返し、初期化のコマンド | 中核の実行の外側のループ。試行ごとに`Init`から始める |
| 試行の間で実行全体の時間窓を待つこと、待つ間の中断と時間切れ | 中核の実行の外側のループ。中核の`RequestWindow`と`UserAbort`、`FinishTimeUp`は変えない |

## 状態機械の外の新しいループ(試行のループ)【ユーザー承認済み】(判定の順序と期限の扱いの細部は【親】)

試行を繰り返す実行ループの外側に、中核の状態機械とは別のループを1つ足す。中核のspecには入らないので、TLA+ではなく性質テストで確かめる。

1段ごとの流れは次のとおり。

1. 試行を始めるかの判定(S-099)。初期化のコマンドの前に、次の順で確かめる。
   1. 利用者による中断を受けていれば、始めずに台帳を書いて終える(S-098)。
   2. 実行全体の期限を過ぎていれば、始めずに時間切れとして台帳を書いて終える(S-094)。
   3. 試行の回数に達していれば、始めずに台帳を書いて終える。
   4. 実行全体の今の窓の残りから最初のページの表示の1回を引いた数が上限の半分を下回れば、窓が明けるまで待ち、1に戻る(S-097, S-098)。
2. 初期化のコマンドを実行する(S-028, S-088〜S-090)。失敗したら、終えた試行までで台帳を書き、終了コード3で終える(S-089)。実行中に期限に達しても終わるのを待ち、そのあと試行を始めずに打ち切る(S-100)。
3. ブラウザを開き、認証状態を入れ、最初のページを表示する(S-027)。最初の表示を実行全体の窓に1回数える(S-097)。この間に期限に達したら、待たずに打ち切る(S-100)。
4. 中核を1回実行する。時刻は実行の開始からの経過時間、時間窓の上限は1の4で求めた値、期限は実行全体の期限を渡す(S-094, S-097)。中核が対象サーバーへアクセスするたびに、実行全体の窓にも数える。
5. 試行の結末を決める(S-049, S-093)。中断か時間切れで終わった試行は打ち切りで、ほかは終えた試行である。1に戻る。

判定軸:
- 期限: 実行の開始からの経過時間が、設定の制限時間以上か。
- 窓の残り: 上限−u−1が上限の半分以上か(上限が奇数でも「2倍が上限以上か」で判定する)。uは実行全体の今の窓に数えたアクセスの数。
- 試行の回数: 始めた試行のうち終えたものと打ち切りを合わせた数が、設定の回数に達したか。

性質テストで確かめること(試行の長さ、試行を始める時刻、各試行のアクセスの数と時刻、初期化のコマンドとブラウザの起動にかかる時間を乱数で作り、偽の時計で回す):
- どの実行全体の窓でも、数えたアクセス(最初の表示を含み、初期化のコマンドの分を除く)は上限以下である。
- 期限を過ぎた時刻に、初期化のコマンドもブラウザの起動も始まっていない。
- 終えた試行と打ち切りの試行の数の和は、始めた試行の数に等しい。打ち切りは1回の実行で多くても1回である。
- 待っている間に中断か期限が来たら、次の窓を待たずに終える。
- 終えた試行の数は設定の試行の回数以下である。

## 設計メモ(ID別の補足・他IDとの関係)

1. **状態機械に近かった点(S-012, S-015, S-045, S-050, S-054, S-094, S-097〜S-100)**: どれも遷移を変えずに済む解釈を採った。別の解釈を採るとspecが変わるので、そのときは仕様に戻ってTLA+の検査をやり直す。
   - a. 試行をまたいだ判断予算と時間窓(S-012, S-094, S-097〜S-101)
      - 出発点: 設計は「試行どうしは互いに影響しない」(L114)と「負荷制御を共有する」(L60)を書くが、予算と時間窓を試行をまたいで持ち越すかは書いていない。持ち越すと中核の`Init`の値が変わり、既存のspecの`StartsFresh`も変わる。そこで、判断予算・中核の時間窓の回数・カウンタは試行ごとに`Init`から数え直す(S-094、【親】)。これだけでは、短い試行を続けると1時間あたりの対象サーバーへのアクセスが既存S-042の上限の試行の回数倍まで届きうる。
      - 【ユーザー】2026-10-18に、ユーザーが「試行の間で待つ」と決めた。ここまでがユーザーの決定で、以下の中身は親の判断である。
      - 【親】待ち方の経緯: 「実行全体の今の窓に1回でもアクセスがあれば待つ」は実質1時間に1試行になるので替えた。「残りを中核の上限にして0のときだけ待つ」は、中核の窓を試行の開始から区切ると窓がずれて上限を超えうるので替えた。最後に次の4つにした(S-097)。
        - (1) 中核に渡す時刻は、実行の開始からの経過時間にする。中核の窓の区切りが実行全体の窓とそろう。中核の初期状態の窓の回数は0のまま。窓の番号は渡された時刻から求める実装の詳細で、specの状態ではない。窓の満了は既存のspecの`ResetRequestWindow`(いつでも起こりうる環境の事象)のままなので、遷移は変わらない。
        - (2) 試行の最初のページの表示(認証状態を入れたあとの最初の遷移)も、実行全体の窓に1回数える(E2)。中核の外で起きるアクセスなので、中核に渡す上限は「残り−1」にする。
        - (3) 中核に渡す上限は、試行を始めたときの値のまま、その試行の間は変えない。後の窓でも低いままなので安全側である。上限は中核では定数`MaxRequests`なので、試行ごとに値を変えても遷移は変わらない。
        - (4) 「残り−1」が上限の半分を下回るときは次の窓まで待ち、「上限−1」で始める。上限が奇数のときも「2倍が上限より小さい」で判定する。上限が1だと「上限−1」が0になり始められないので、インタビューのモードでは上限を2以上に限る(S-083の3行目、【親】)。feature の境界は、上限10で、使った回数0(渡す上限9)と4(渡す上限5、ちょうど半分)で待たずに始め、5(渡す上限4、半分を1下回る)と10(残り0)で待つ。
      - 上限が守られる理由: 窓の区切りがそろうので、試行を始めた窓に入るのは、前の試行の分u、最初の表示の1回、今の試行の中核の分(上限−u−1以下)だけで、和は上限以下になる。初期化のコマンドとブラウザの起動のあいだに窓が明けても、渡す上限は新しい窓の残りより小さいので安全側である。後の窓では、前の試行の分は無く、今の試行の分は上限−1以下である。
      - 【親】初期化のコマンドのアクセス(S-101): ツールからは数えられないので数えない。その負荷は利用者の責任であることを利用者向けの説明に書く。性質テストの「どの窓でも上限以下」も、この分を除いて数える。
      - 【親】試行の回数の上限(S-083): 1回の実行で試行は100回までとし、超える設定は拒否する(E2/C6)。判断モデルの呼び出しの総数は、試行の回数×判断予算と自然さの問いの上限で上から押さえられる。
      - 【親】制限時間(S-094の2行目): 待つ間に時間切れが効くには、試行の外にも期限が要る。そこで制限時間は実行の開始から測り、試行をまたいで引き継ぐ。中核には各試行で同じ期限を渡すので、specでは`TimeElapses`が起きる時点が変わるだけで、遷移は変わらない。期限で切られた試行は打ち切りとし、Nにも目的に届かない試行にも数えない(E1、S-049, S-093)。
      - 【親】外側のループ(S-099、E3): 試行を始めるかの判定は初期化のコマンドの前に行い、中断、期限、試行の回数、窓の残りの順に確かめる。流れ、判定軸、性質テストは「状態機械の外の新しいループ」の節に書いた。【親】初期化のコマンドの最中に期限が来たら、コマンドは途中で止めずに設定の待ち時間まで終わりを待つ。対象サーバーの状態を中途半端に残さないためである。ブラウザの起動中は、止めても対象サーバーの状態が変わらないので、待たずに打ち切る(S-100)。
   - b. 候補を絞らない選び方(S-050): 既存の中核の候補の絞り込みは、問いの選択肢を作る関数で、specでは`RequestDecision`の中身(モデル外)である。使わなくても遷移は変わらない。
   - c. 【親】目的を書かない試行(S-045): 既存の決め打ちシナリオの道筋に乗せるため、done_whenが成り立たない段階を1つ持つ試行として扱う。宣言が0個のdone_whenを「すべて成り立つ」と読むと、最初の確認でゴール達成になってしまう。宣言が空の段階を作らず、成り立たない段階として表す(実装の注意)。目的を書くときは、done_whenに宣言が1つ以上要る(S-078の検査の例)。
   - d. 【親】自然さの問い(S-054, S-102、E4): 試行の中で問うと`RequestDecision`が増え、判断予算と待機中の優先順位に関わる。そこで、すべての試行を終えて課題をまとめたあと、実行ループの外で課題の番号ごとに1回だけ問う。この問いは判断予算に数えない。回数は設定の上限(既定50)までとし、台帳の並び(割合の降順、同率は番号の昇順)の先頭から問う。上限を超えた課題は「確かめられなかった」区分に入れる(並びの順に問うことは【親】)。
2. **共有部分の参照(S-011〜S-014)**: 既存台帳の要件をそのまま使い、このモードの台帳では抜き出し直さない。feature でも、代表の例でこのモードでも効くことを確かめるだけにした(既存の受け入れシナリオはS-082で通り続ける)。
3. **派生の要件(S-042, S-055, S-084〜S-104)**: 設計に直接の文が無く、unwantedの系統生成、STRIDE・CWE、レビューの指摘から立てた。出どころは各行の印(【ユーザー】【ユーザー承認済み】【親】)で分けた。もとは【推測】だったものも、2026-10-18 に親が1つずつ確かめて【親】に確定した。終了コードは既存の決まり(設定エラーは2、実行時エラーは3、参考情報は数えない)にそろえた。
4. **設計の文書だけでは決められず埋めた点(どれも【親】(2026-10-18 に親が確かめた)。ユーザーが決めたものや承認したものはその旨を書く)**
   - a. 目的の推測の問い(S-040): 設計L149は「目的が書かれていないとき」に推測を問うと書くが、L94-95は書いた目的と推測の両方があるときの扱いを書く。両方が起きるように、目的を書いたときも推測を問うとした。ずれを比べる範囲は【親】の判断(E5/C4)で決めた。実行の目的は1つで、任意で画面ごとの目的(URLの型で画面を指す)を書ける。ずれは画面ごとの目的を書いた画面でだけ比べ、種類「目的のずれ」の課題にする(S-021, S-103)。
   - b. 「確信度が低い」の閾値(S-051): 設計に値が無い。迷いの度合いの閾値と別の、迷いとみなす確信度の閾値を設定に持たせた(S-083)。境界は「閾値未満で迷い」とした。迷いの度合いは既存のエラー表示と同じく「閾値以上で記録」とした。
   - c. 「同じ画面を行き来した」の定義(S-048): 同じ2つの画面の間を往復したこと(A→B→A→B)とした。
   - d. 中断した試行の数え方(S-049, S-093): 設計L167を字義どおり読むと、中断で終わった試行も目的に届かないに入る。利用者の中断から目的に届かない課題が出るのは誤りなので、中断した試行は回数にも数えないとした。残りの試行はせず、終えた試行までで台帳を書く。期限で切られた試行も同じく打ち切りとするのは【親】の判断(E1)。終えた試行が0回なら、割合も課題も出さない(CWE-369)。
   - e. 直す指示の文を誰が作るか(S-060): 設計に書いていない。判断モデルの文をもとに作る前提で、1行に収めることと構造の無害化(S-084)だけを要件にした。
   - f. 見えにくい要素の答えの形(S-039): 台帳に要素の役割・名前・位置を書くため、要素の番号の一覧と理由の文で受け取るとした。
   - g. 判断モデルが画像を扱えないとき(S-031, S-034): 設計は未確定とする。【ユーザー承認済み】の判断(N2、記録7)で、判断モデルのアダプタが起動のときに画像を扱えるかを申告する形にした。申告は判断モデルの抽象の側に持たせ、台本どおりに答えるスタブ、橋渡し、後で足す直結のアダプタのどれも申告する(【ユーザー承認済み】C21)。橋渡しはJSONの版の項目で申告する。扱えないと申告したら、見えにくい要素の答えを必須から外し(S-042の対象外)、視認性の課題は出さず、そのことを台帳に書く。扱えると申告したのに答えが無いときは、今どおり応答の異常とする。扱えないと申告した橋渡しには、スクリーンショットを送らない(【ユーザー承認済み】、記録7)。使われないうえ、外へ出る情報が増えるだけだからである。撮ったスクリーンショットの場所は今どおり台帳に残す。
   - h. 同じ割合の課題の並び(S-061): 課題の番号の順とした。
   - i. 解消の条件(S-070, S-071): 【ユーザー】(回答5)が「届いた回数で比べる」と決めた。今回その画面に届いた試行の数が、前回その画面に届いた試行の数以上で、1回も起きなかったときだけ解消とする。届いた数が足りなければ(0を含む)「確かめられなかった」に分ける。そのため、台帳の各課題に、その画面に届いた試行の数を書く(S-058)。前の版の「試行の総数Nで比べる」と「どれか1つの試行が届けばよい」(C5)は、これで置き換えた。照らし合わせの分け方は4つで、設計の文書もすでに4つに直した。
   - j. 形式の検査のサブコマンドの終了コード(S-078): 設定エラーと同じ2にした。目的の設定も検査の対象にした(設計L35「ペルソナと目的を…検査のコマンド」)。
   - k. 閾値の値域(S-083): 迷いの度合いと確信度の閾値は、既存の確信度の閾値と同じく0より大きく1以下とした。
   - l. 終了コード(S-095): インタビューの課題は判断モデルの判断だけによるので、既存S-029の参考情報と同じく終了コードに数えないとした。既存の確定の問題(コンソールエラーなど)の記録はこのモードでも共有する(S-014)。
   - m. 前回の台帳の読み戻しの失敗(S-085)と、ペルソナや目的の食い違い(S-086): 設定エラー(終了コード2)で起動しないとした。前回の台帳を渡さないとき(S-096)はすべて新しく出たとした。目的を推測させた実行どうしは、推測の印と開始のURLが同じなら比べ、推測した文は比べない(【親】E6)。推測の文は試行ごとに揺れるので、文で比べると照らし合わせがほぼできないためである。
   - n. 初期化のコマンド(S-089, S-090): 失敗したら実行を止めて終了コード3とした(汚れた状態で試すと試行が互いに影響するため)。初期化のコマンドを呼べることは【ユーザー】(回答2)が決めた。失敗したら止めることは【親】。止める前に終えた試行までの台帳を書くのは【親】の判断(C11)。APIキーを渡さないことと、出力を伏せることは、既存の外部コマンドの扱いから足した(【親】)。
   - p. スクリーンショットの名前(S-104): 課題の番号とステップから作り、パスの区切りを含めないのは【親】の判断(C7)。同じ課題が複数の試行で同じステップ番号に出ると名前がぶつかるので、試行の番号も入れた(【親】)。課題の番号はツールが決める記号で、判断モデルやページの文字を含まない。
   - o. TUIの書き戻しの競合(S-087): 設計に書いていない。外での書き換えを上書きしないとした。既存の`docs/architecture.md`の「TUIからの操作は終了だけにし、実行の状態は変えない」は、実行中の画面についての決まりで、台帳の画面の書き戻しとは別とした。
5. **S-001の3種類と目的のずれ**: 目的のずれ(S-021, S-103)は、3種類のうち「目的に届かない」(設計の「画面の目的にたどり着かない」)の一部とみなす(【親】C15)。台帳では種類を分けて書くが、3種類の数え方では目的に届かないに含める。
6. **目的のずれの判定(S-021, S-102, S-103)**: 【親】の判断で、ずれは文字列の一致で決めず、試行をすべて終えたあと、判断モデルに別の問いとして聞くことにした。問いの単位は画面ごとの目的の1項目(URLの型1つ)である。その型に合う画面で、終えた試行の中に出た推測を全部(前後の空白を除いた文字列で重複をまとめたもの)と書いた目的を渡し、「これらの推測は書いた目的と同じことを指すか」を1回だけ聞く。同じでないと答えたら、その項目の目的のずれの課題にする。同じ型に合う画面が複数あっても(例: `/products/42`と`/products/43`)、推測をまとめて1回だけ聞く。型に合う画面に届いた終えた試行が無いか、使える推測が1つも無ければ聞かない。打ち切りの試行の推測は数えない(C17と同じ)。この問いは自然さの問いと同じ上限(既定50)に数え、上限を超えた分と答えが使えないときは、ずれの課題を出さず「確かめられなかった」区分に入れる。試行の中の判断予算には数えない。上限の中では、ずれの問いを先に、自然さの問いを後に聞く。ずれの問いで出た課題も、自然さの問いにかける(どちらも【親】)。前の版の「最も多く出た推測を聞く」とその同数の規則は、推測を全部渡すので要らなくなり、消した。
