# インタビューのモードの課題を測る仕組み(#80)

## 目的

インタビューのモードが出す課題が、本物の使いにくさをどれだけ捉えるかを数字で測る。
既知の使いにくさを仕込んだ小さなサイトで回し、仕込みと台帳の課題を突き合わせて、再現率と適合率を出す。

数字は、インタビューのモードを作り込み続けるかを利用者が決める材料にする。
判断の線は先に決めず、種類ごとの数字と課題の中身を見て利用者が決める(利用者、2026-10-20)。
同じ物差しで、#86 などの直しの前後も比べる。

根拠は `tasks/reviews/2026-10-20-ai-persona-review.md` の指摘4。
AIの指摘の適合率は人の0.83に対して0.60という報告がある(Duan et al.)。

## 決めたこと

- サイトの題材は、勤怠管理システムを比べる比較サイトの小型版にする。it-trend.jp で使った総務担当のペルソナをそのまま使え、実物での結果とも比べやすい(利用者)。
- 仕込みに当たらない課題は、人が「本当に使いにくい(仕込み忘れ)」か「誤り」を付ける。外れに数えるのは「誤り」だけにする。付けた判断は次の測定に引き継ぐ。何も除かない厳しい数字も並べて出す(利用者)。
- 測定は手元で手動に回す。同じ設定(試行3回)を3回回し、平均とばらつきを出す。CI では回さない(利用者)。
- 部品は新しいクレート `crates/webqa-eval` に置く。台帳は既存の `webqa_core::interview::ledger::read` で読み、読み方を二重に持たない。製品の CLI には何も足さない(利用者が案Aを選んだ)。

## 構成

### サイト(`eval/site/`)

静的な HTML で5画面ほど作る。

| 画面 | パス | 役目 |
|---|---|---|
| トップ | `/` | 検索欄と分類へのリンク |
| 検索結果 | `/search.html` | 検索語に合う製品の一覧 |
| 分類の一覧 | `/attendance.html` | 勤怠管理の製品の一覧 |
| 製品の詳細 | `/product-*.html` | 機能と料金 |
| 資料請求 | `/request.html` | 入力欄と送信。送信の先はガードレールで止まる |

台帳の4つの種類それぞれに、2〜3個ずつ使いにくさを仕込む。

| 種類 | 仕込みの例 |
|---|---|
| 視認性が悪い | 薄い色の小さな「料金を見る」のリンク |
| 判断に迷う | 意味の違いが分からない「次へ」と「進む」が並ぶ |
| 目的に届かない | 製品の料金を比べる手段がどの画面にも無い |
| 目的のずれ | 一覧の題と中身が合わない |

仕込んだところ以外は、素直に作る。
仕込み忘れの本物の使いにくさは、人の判断で拾う。

### 目的の文書(`eval/purpose.yaml`)

目的は推測させず、文書で渡す。
目的のずれの課題は、画面ごとの目的を書いたときだけ出るためである。
目的に届かない課題を判定するため、達成の条件(`done_when`)も書く。
目的は「勤怠管理システムを料金と機能で比べ、候補を2〜3個に絞る」とする。
画面ごとの目的は、5画面それぞれに URL の型で書く。

### 正解表(`eval/truth.yaml`)

仕込みごとに1件書く。

- `id`: 仕込みの名前(例 `faint-price-link`)
- `kind`: 台帳の種類の表示名(視認性が悪い、判断に迷う、目的に届かない、目的のずれ)
- `path`: 画面のパス。目的のずれは、目的の文書に書いた URL の型。目的に届かないは、試行が止まる画面を前もって決められないので省き、種類だけで突き合わせる
- `element`: 役割と名前。要素に結びつかない種類では省く
- `note`: 何を仕込んだか

### 人の判断(`eval/labels.yaml`)

仕込みに当たらなかった課題に、人が判断を付ける。
キーは種類、パス、要素(あれば)で、値は `real`(本当に使いにくい)か `false`(誤り)。
一度付けた判断は次の測定でも使う。
判断が無い課題は未判定として数え、一覧に出す。

### 採点(`webqa-eval score`)

台帳(`ledger.md`)と正解表と人の判断を読み、結果を出す。

- 台帳の課題のうち、本体と確かめられなかった課題を数える。ペルソナから外れると判断した課題は数えない。
- 台帳の課題と正解表の行は、種類と画面のパス(目的のずれは URL の型)が一致し、正解表に要素があればその役割と名前も一致したときに当たりとする。
- 再現率 = 当たった仕込みの数 ÷ 仕込みの数。
- 適合率は2通り出す。
  - 厳しい数字 = 仕込みに当たった課題の数 ÷ 課題の数。
  - 人の判断を引いた数字 = (仕込みに当たった課題 + `real` の課題) ÷ (課題の数 − 未判定の課題)。
- 種類ごとと全体の数字、仕込みに当たらなかった課題の一覧、見つからなかった仕込みの一覧を、Markdown の表で出す。

### 配信(`webqa-eval serve`)

`127.0.0.1` の空いたポートで `eval/site/` を配り、URL を標準出力に書く。
既存の CLI のテストのやり方(`crates/webqa/tests/cli/site.rs`)に倣う。
`file://` はガードレールの許可するオリジンを作れないので使わない。

### 回し方(`just eval`)

1. `webqa-eval serve` でサイトを立てる。
2. 設定(`eval/config.yaml`。ペルソナは it-trend.jp と同じ、試行3回)の `target.url` をサイトの URL にして、インタビューのモードを回す。
3. 1と2を3回繰り返す。
4. 3つの台帳を採点し、平均とばらつきを出す。
5. 結果を `tasks/eval/<日付>.md` に残す。費用は Gateway の費用の記録で確かめて書く。

判断モデルは `bridge/jev.py`(JEV 1.14.0 と Haiku 5.5)を使う。
キーは本体の checkout の `.env` から読むので、本体の checkout の直下で回す。
費用の見込みは1回(試行3回)あたり1ドル前後。測る前に単価を確かめる。

## テスト

- 採点は単体テストで確かめる(当たり、外れ、要素の有無、未判定、人の判断、ゼロ除算、ペルソナから外れた課題を数えないこと)。カバレッジ100%の決まりに乗る。
- 配信は、ページを返すこと、無いパスに404を返すことを単体か結合のテストで確かめる。
- 台本の判断モデル(`crates/webqa/tests/fixtures/cli/bridge.sh` の形)でインタビューのモードを回し、採点まで通る結合テストを1本置く。本物の判断モデルでの測定はテストにしない。
- 新しいクレートと `eval/` は、PR の CI の判定の対象(`scripts/ci_changes.py` の `CODE`)に足す。

## 範囲の外

- 題材を増やすこと。
- CI での定期的な測定。
- 実物のサイトの課題に人がラベルを付けること(レビューの指摘4の後半)。
- 判断の線を決めること(数字を見てから利用者が決める)。
