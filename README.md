# webqa-explorer

Webサービス向けの探索的テストエージェント。
軽量な判断モデルに画面のアクセシビリティ情報を渡し、返ってきた操作をブラウザで実行する。
これを繰り返して画面を自律的に探索し、不具合や表示の違和感、アクセシビリティ上の問題を見つける。
実装はRustで、状況の表示にはtearsによるTUIを使う。

設計した使い方は3つある。

- 探索モード: 画面を網羅的に操作して、不具合を探す。
- 決め打ちシナリオ: 決めた段階を順にたどり、途中で起きる問題を記録する。
- インタビューのモード: ペルソナを持たせたエージェントに画面を触らせる。
  迷うところ、見えにくいところ、画面の目的にたどり着かないところを、直す指示の台帳として出す。
  見えにくいところを見つけるには、画像を読める判断モデルが要る。

## ほかの道具との違い

以下は設計で決めた性質で、実装は途中にある。

### スクリプトを書くE2Eテストのフレームワーク

E2Eテストのフレームワークでは、人が操作の手順と期待値を書く。
確かめられるのは、書いた手順の上で起きることだけである。

このツールは手順を書かずに、判断モデルが画面を読んで次の操作を選ぶ。
誰もテストを書いていない画面や、思いつかなかった操作の順番でも、おかしくなっているところを見つけられる。
既存のE2Eテストを置き換えるものではない。
書いた手順の外で起きることを探すために使う。

### 判断モデルにブラウザを操作させる道具

判断モデルにブラウザを自由に操作させる道具は柔軟だが、多くは操作の安全を判断モデルの判断に委ねる。

このツールは、判断モデルの出力を信用しない前提で設計した。

- 購入、削除、退会、サインインに当たる語を名前に持つ要素や、それに当たる送信先へ送る要素は、判断モデルの外にある判定で操作しない。
  課金画面に入ったら離脱する。
  語の一覧は設定で足せる。
- 許可したドメインの外に出たら、そこでは操作せずに戻る。
- 対象サーバーへの1時間あたりのアクセスの回数と、判断モデルの呼び出しの回数に上限を設ける。
  実行の時間の上限も設定できる。
  上限を設定しておけば、夜間に放っておいても相手のサーバーに負荷をかけすぎない。
  判断モデルの呼び出しの回数に上限があるので、1回の実行の費用にも上限がつく。
- 終了の条件と優先順位を状態機械として書き、TLA+の小さなモデルで全状態を検査した。
- 実行の記録を台本にして、同じ判断の列で探索をやり直せる。
- 探索モードと決め打ちシナリオでは、判断モデルにアクセシビリティ情報のテキストだけを渡す。
  画像を送らないぶん、問い合わせが小さい。
- 確定の問題の有無を終了コードで返すので、CIに組み込める。
  わかりにくい表示のような、意味の判断が要る検出は参考情報にして数えない。

### テスト自動化のサービス

テスト自動化のサービスは、操作の記録と再生や、要素の指定が合わなくなったときの自動修復を得意にする。
中心になるのは登録したシナリオの再生で、画面の情報をサービスの側に送る形のものが多い。

このツールの実行は手元やCIの中で行い、外へ出るのは判断モデルへの問い合わせだけである。
送る前に、設定で指定した機密情報を伏せる。
伏せるのは設定で指定した値だけなので、画面に出たほかの情報は判断モデルへ送られる。
そのため、どのモードもテスト環境で使う前提にしている。
インタビューのモードは、それに加えて画面のスクリーンショットを伏せずに丸ごと送る。
判断モデルは外部コマンドとの橋渡しで差し替えられる。
ただし、インタビューのモードで見えにくいところを見つけるには、画像を読める判断モデルが要る。

## このツールの価値

自律的な探索、操作の安全、再現できる記録、使いやすさの課題の洗い出しは、それぞれならほかの道具にもある。
このツールは、これらを1つにまとめることを狙って作っている。
判断モデルの答えに関係なく効くガードレールの上で、設計を検査した状態機械が探索を進める。
インタビューのモードでは、ペルソナから外れた報告を分けて扱い、課題をAIに渡せる直す指示としてMarkdownの台帳に出す。
利用者は台帳から直す課題を選んでAIに直させ、再実行して照らし合わせる。
照らし合わせでは、課題を解消・残存・新規・確かめられなかった、に分ける。
解消と見なすのは、その画面に届いた試行の数が前回以上で、1回も起きなかったときだけである。
課題ごとに、何回の試行のうち何回起きたかも示す。

インタビューのモードは、ユーザーインタビューの代わりに、使いやすさの改善を何度も回すためのものである。
利用者のニーズや動機を調べることは目的にしていない。
それは人に聞く。
