# ペルソナと目的を書く

`webqa interview`に渡す2つの文書を書く。
ペルソナの文書は、画面を触る人物を決める。
目的の設定は、その人物が何をしに来たかと、どこまで来たら終わりかを決める。
どちらもYAMLで書く。

## ペルソナを書く

インタビューのメモや分析のデータを読み、次の5項目を埋める。
実在の人や会社の名前は書かない。
メモに出てくる人が特定できる書き方もしない。

- `name`: 呼び名。メモに実名があっても、架空の名前に置き換える。
- `profile`: 年代、立場、サービスを使う場面を1文で書く。
- `it_literacy`: 何ができて、何を知らないかを書く。
  「得意」「苦手」だけで済ませず、知っている言葉を挙げる。
- `wants`: サービスで済ませたいことを1つ書く。
- `avoids`: この人がしない操作と、知らない言葉を並べる。
  1つ以上要る。

メモにない項目は、推測で埋めずに、書き手に聞く。

```yaml
name: 佐藤さん
profile: 60代。孫に頼まれて、週末にスマートフォンで買い物をする
it_literacy: スマートフォンの基本操作だけ。「カート」の意味は知っている
wants: 孫の誕生日プレゼントを注文する
avoids:
  - URLを手で打たない
  - 「SKU」のような略語を知らない
```

## 目的を書く

目的の設定は`goal`と`done_when`を持つ。

- `goal`: 人物が画面で目指すことを1文で書く。
- `done_when`: 終わったと見なす条件を書く。
  `url`(着いたパス)、`element`(出ている要素)、`text`(出ている文言)の
  どれかを1つ以上書く。

### done_whenは確認の画面で終える

`done_when`は、確定の操作ができる画面まで来たことで書く。
確定の操作そのものを実行したことでは書かない。
インタビューのモードは、注文の確定や送信のボタンを押さずに止まる。
操作を実行した後の画面を条件にすると、永遠に満たされない。

- 良い例: 注文の確認画面のパス`/order/confirm`に着いたこと。
- 悪い例: 注文完了画面のパス`/order/done`に着いたこと。

```yaml
goal: 注文を確定できる画面まで進む
done_when:
  url: /order/confirm
```

## 書いたあとに確かめる

書いた文書は、ファイルに保存して、次のコマンドで確かめる。

```text
webqa check-docs persona persona.yaml
webqa check-docs purpose purpose.yaml
```

正しければ、何も表示せずに終わる。
誤りがあれば、項目の名前を含む文が表示される。
その項目を直して、もう一度確かめる。
何も表示されなくなるまで繰り返す。
